# FD-08: Port the automation rules to TypeScript

## Summary

The five mailroom rules (`reopen-on-reply`, `tag-billing`, `escalate-vip`,
`assign-round-robin`, `auto-close-stale`) exist only as CommonJS in
`legacy/rules/`. `apps/api/src/rules/` does not exist, so `npm run rules:parity`
reports "typescript not written yet" for all five. The work is a pure port: five
self-contained TypeScript modules plus a small shared types/helper module and unit
tests that replay the golden fixtures. No change to the contract, the API
routes, the database, the mailroom, the cron jobs, the finance export or the seed
data. Switching the mailroom over to the TS rules is explicitly out of scope.

## Kind

missing-feature

## Root cause (with path:line evidence)

What is absent: `apps/api/src/rules/<name>.ts` for each of the five rules. The
parity script looks there and nowhere else:

- `scripts/rules-parity.ts:140-147` builds `apps/api/src/rules/<name>.ts`, returns
  `null` if it does not exist ("not written yet", line 172), otherwise imports it and
  takes `mod.rule ?? mod.default`.
- Baseline run on main (`TZ=UTC npm run rules:parity`): legacy 10/10, 7/7, 7/7,
  7/7, 9/9; typescript "not written yet" for every rule. Exit 0, so the item is not
  yet proven by parity.

The contract the port has to honour, all from the parity harness and the legacy
rules:

- Rule shape `{ name, when(ticket), run(ticket, ctx, cb?) }`:
  `scripts/rules-parity.ts:40-44`, `legacy/rules/index.js:6-12`.
- `run` may call `cb` or return a promise; the harness guards against both:
  `scripts/rules-parity.ts:95-113`.
- `ctx` = `{ now: Date, teammates, setStatus, assign, addTag, log }`; each mutator
  takes an optional callback **and** returns a promise in the harness
  (`scripts/rules-parity.ts:70-93`), but is callback-only, with a **required**
  callback, in the real mailroom context (`legacy/rules/context.js:79-138`: each
  mutator calls `done(...)` unconditionally). `ctx.log` prefixes `[rules] ` itself
  (`legacy/rules/context.js:134-136`).
- Ticket shape (`RuleTicket`): `legacy/rules/context.js:16-28`. Every case in all five
  `fixtures/rules/*.json` files carries all ten keys (checked with a script over the
  fixtures), and `legacy/test/rules/record.js:43-57` builds full tickets too.
- Effects are compared with `isDeepStrictEqual` and order matters
  (`scripts/rules-parity.ts:127-128`).
- **One rule instance runs all cases in order**, with a fresh ctx per case
  (`scripts/rules-parity.ts:117-123`); `fixtures/rules/assign-round-robin.json:3`
  says the rotation carries from case to case.
- `rules:parity` only `require`s `legacy/rules/<name>.js` (`scripts/rules-parity.ts:166`),
  and none of the five rule files requires anything, so parity never loads the
  mailroom's config, database or lock. It needs no `FRONT_DESK_DB`/`MAILROOM_LOCK`.

**Scope of "reproduced exactly" (round 1, N6).** Parity is promised for every input
the mailroom's `loadTicket` can produce, which is what the typed `RuleTicket` allows:
`created_at`/`updated_at` are `NOT NULL` (`legacy/db/schema.sql:25-26`), `customer`
comes from an inner `JOIN` so it is always present (`legacy/rules/context.js:37-38`),
and `closed_at` is nullable (`legacy/db/schema.sql:27`), so the only reachable quirk

comparisons), which also keeps the legacy result for unparseable date strings, but no
test pins those. Inputs outside the type (missing `customer`, missing `updated_at`)
are not covered: don't add defensive defaults for them, and don't test them.

## Implementation plan

All commands from the worktree root, with `TZ=UTC`.

1. **Shared types and helpers**: create `apps/api/src/rules/rule.ts` (any name
   that is not one of the five rule names). Contents:
   - `Done`, `RuleTicket` (mirror `legacy/rules/context.js:16-28` exactly: all ten
     fields required, `closed_at: string | null`, `message: {...} | null`,
     `customer: { name: string | null; email: string; vip: boolean }`), `Teammate`
     (`{ id: number; name: string; email?: string }`; `legacy/test/rules/record.js:6`
     passes teammates without email), `RuleContext` (`now: Date; teammates: Teammate[];`
     `setStatus/assign/addTag(arg, done?: Done): Promise<void> | void; log(line: string): void`),
     `Rule` (`name: string; when(ticket: RuleTicket): boolean;`
     `run(ticket: RuleTicket, ctx: RuleContext, done?: Done): Promise<void>`).
   - `perform(start: (done: Done) => Promise<void> | void): Promise<void>`: calls a
     ctx method with a callback **always** (the mailroom ctx crashes without one) and
     also honours a returned promise; settles once, on whichever comes first; rejects
     on an error from either. This makes the rules work with the harness ctx (both),
     the real mailroom ctx (callback only) and a promise-only ctx.
   - `defineRule({ name, when, run: async (ticket, ctx) => ... }): Rule`. Its `run`
     (round 1, N4):
     - **without** `done`: returns the rule's promise; it rejects on error.
     - **with** `done`: calls `done(null)` on success or `done(err)` on error, exactly
       once and never synchronously, and returns a promise that **resolves** after
       `done` has been called, in both cases. It must not reject, because the mailroom
       runner ignores `run`'s return value (`legacy/rules/index.js:42-46`) and a
       rejected promise there would be an unhandled rejection after the switch-over.
       The parity harness calls `done` first and its once-guard ignores the later
       resolution (`scripts/rules-parity.ts:98-108`), so parity still sees the error.
       An exception thrown by `done` itself is not caught and re-delivered.
   - No imports at all (and certainly nothing from `legacy/` or `../legacy-adapter.ts`).
   - Check: `npx tsc --noEmit -p apps/api/tsconfig.json`.
2. **Write the failing test first** (see Failing test proposal) at
   `apps/api/src/rules/rules.test.ts`, before any rule file exists. Check it fails
   5/5 on the assertion: `TZ=UTC npx vitest run --project api src/rules/rules.test.ts`.
   Keep that output for the hand-off (round 1, N9: no separate commit is required;
   committing is the user's call).
3. **Port the four stateless rules**, one file each, each exporting
   `export const rule = defineRule({...})`:
   `apps/api/src/rules/reopen-on-reply.ts`, `tag-billing.ts`, `escalate-vip.ts`,
   `auto-close-stale.ts`. Take time only from `ctx.now`, teammates only from
   `ctx.teammates`, and make every change via `await perform((done) => ctx.x(..., done))`.
   Keep constants (`DAY`, `WAIT_DAYS`, `VIP_WAIT_DAYS`, `REOPEN_WITHIN_DAYS`, the two
   regexes) local to each file. Emit the **same** `ctx.log` lines as the mailroom,
   without the `[rules] ` prefix, which the ctx adds (round 1, N5; see the table).
   Header comment explains the rule (wording like "the mailroom's rule"; prefer
   "mailroom" to "legacy" in prose). The only import allowed is `./rule.ts`.
   Check per rule: `TZ=UTC npm run rules:parity -- <name>`.
4. **Port assign-round-robin with a factory**: `apps/api/src/rules/assign-round-robin.ts`
   exports `createAssignRoundRobin(): Rule` (rotation `let next = 0` in the closure)
   and `export const rule = createAssignRoundRobin()`. The exported singleton keeps
   the rotation across calls, which parity requires; tests build fresh instances
   so they stay order-independent under `--sequence.shuffle`. Advance `next` only
   after the spam and empty-teammates checks, as legacy does.
   Check: `TZ=UTC npm run rules:parity -- assign-round-robin` (10/10).
5. **Extra unit tests** (round 1, N7). Three more files, all in `apps/api/src/rules/`:
   - `imports.test.ts` (AC 3, round 1, N8). Read every `.ts` file in the folder and
     extract specifiers from `from '...'`, `import('...')`, `require('...')` and bare
     `import '...'` (strip `//` and `/* */` comments first). Non-test files: every
     specifier must start with `./`, contain no further `/`, end in `.ts`, and name a
     file that exists in the folder. `*.test.ts` files: may also import `vitest` and
     `node:*`. Assert with the offending file and specifier in the message. This is

     (`apps/api/src/legacy-adapter.ts:49`, `apps/api/package.json:12`). It lives in its
     own file so the failing-test run in step 2 shows exactly 5 failures.
   - `assign-round-robin.test.ts`, each `it` building its own instances with
     `createAssignRoundRobin()` and teammates `[{id:1},{id:2},{id:3}]` (names filled in):
     - two instances don't share a rotation: A assigns 1 then 2; a new B assigns 1;
       A then assigns 3.
     - a spam-tagged ticket and a run with `teammates: []` record no effects and
       don't advance: the next normal ticket on the same instance gets teammate 1.
   - `rule.test.ts`, testing `perform`/`defineRule` through the **escalate-vip** rule,
     because it chains two mutators (`addTag` then `assign`) and so catches

       `closing #<id> after 8 days on hold` then records `setStatus 'closed'`.
       Check: `TZ=UTC npx vitest run --project api src/rules`, then the same with

## Failing test proposal

Location: `apps/api/src/rules/rules.test.ts` (picked up by the `api` Vitest

What it does: for each of the five rule names (hard-coded list, not read from

`it` that:

1. If `apps/api/src/rules/<name>.ts` exists, calls `vi.resetModules()` and

3. Replays every case of `fixtures/rules/<name>.json` (path
   `path.resolve(import.meta.dirname, '../../../../fixtures/rules')`) in order,
   against one rule instance, with a recording ctx copied from
   `scripts/rules-parity.ts:70-93` (callback **and** promise), and asserts
   `expect({ when, effects }, case.name).toEqual(case.expected)`.

Constraints (round 1): the file has **no static imports from sibling modules**
(types are declared locally; rules are reached only through the guarded dynamic
import), so it can be dropped onto a clean `main` to reproduce the failure (N9).
It only imports `vitest` and `node:*`, which `imports.test.ts` allows. The import
guard is not in this file, so the failing run is exactly 5 failures (N7).

The existsSync guard is what makes it fail on an assertion rather than on a
module-not-found error. A draft of this file was run in a scratch copy of the
repo: on a tree with no TS rules it fails 5/5 with
`AssertionError: apps/api/src/rules/<name>.ts exports \`rule\` or a default: expected undefined to be '<name>'`;

same way. The draft typechecks under `apps/api/tsconfig.json` and passes ESLint

## Risks

- **Running in the root checkout (B1).** `npm run format` would rewrite other
  agents' worktrees and `tmp/` plans; `npm run check` would lint and format-check
  them. Run everything in a fresh worktree and format only `apps/api/src/rules`.
- **Round-robin state vs. shuffled tests (FD-03 trap).** Parity needs the rotation
  to carry across calls on one imported instance, but CLAUDE.md forbids
  module-level state that leaks between tests, and CI shuffles
  (`.github/workflows/ci.yml:28-38`). Use the factory, replay all round-robin cases
  inside one `it`, and use `vi.resetModules()` or a fresh `createAssignRoundRobin()`
  in every test that runs the rule. Never split the golden cases into one `it` per case.
- **AC 3 is broader than the repo boundary rule.** The rules may not import the
  adapter either. Don't reuse `legacy/rules/context.js` types, `legacy/lib/clock.js`,
  or re-export the CommonJS rule. Rule files import only siblings; `imports.test.ts`
  enforces it.
- **AC 4: don't touch `legacy/rules/` or `fixtures/rules/`**, even to fix the
  round-robin module state or to add a `closed_at: null` case. Those belong to FD-03
  and (if anyone wants it) a later change. If FD-03 lands on `main` first, the
  merge-base diff in step 6 keeps its `legacy/rules/assign-round-robin.js` change out
  of FD-08's AC 4 check; if FD-08 merges first, FD-03's branch must rebase.
- **Callback vs promise ctx.** The harness ctx calls `done` _and_ returns a promise;
  the mailroom ctx only calls back and requires the callback. An `async run` that
  just does `await ctx.assign(id)` passes parity but would crash or resolve early
  against the real ctx. Go through `perform`.
- **Error delivery.** With a `done`, errors go only to `done` and the returned
  promise resolves; without one, the promise rejects (step 1). Getting this wrong
  means an unhandled rejection after the switch-over.
- **Exact boundaries and coercions.** `>` vs `>=` at 14 days (reopen) and 7/14 days
  (auto-close); `!ticket.assignee_id` (0 counts as unassigned); `Boolean(customer.vip)`;
  effect order (`addTag` before `assign`; `billing` before `urgent`). `isDeepStrictEqual`
  also fails on extra keys in an effect.
- **Regex statefulness.** Adding the `g` flag to the tag-billing regexes makes
  `.test()` alternate results between calls.
- **Typecheck includes `acceptance/tsconfig.json`** (`package.json:27`). Held-out
  tests presumably import the new modules, so over-narrow exported types could break
  `npm run check` at the typecheck step. Keep `done` optional, `when`
  synchronous-boolean, ctx mutators returning `Promise<void> | void`, and
  `Teammate.email` optional. `RuleTicket` mirrors the mailroom's full typedef (AC 1
  says "same shape as the mailroom's"); step 7 says how to widen it if typecheck
  objects.
- **Strict TS options.** `noUncheckedIndexedAccess` makes `ctx.teammates[i]`
  possibly undefined (guard it, as the prototype did); `verbatimModuleSyntax`
  requires `import type` for types; relative imports need the `.ts` extension; no
  `any` (ESLint `no-explicit-any`).
- **tsx-loaded at parity time.** The parity script imports each file through tsx,
  so any helper module the rules import must also resolve with a `.ts` extension
  from `apps/api/src/rules/`.
- **Don't wire anything up.** Not in `apps/api/src/server.ts`, not in the mailroom,
  not in `ops/crontab`. `apps/api/test/setup.ts:16` sets `MAILROOM_RULES=off`; the
  mailroom keeps running its own rules in prod.
