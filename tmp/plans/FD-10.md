# FD-10: Collapse `state` into `status` (triage plan)

## Summary

`tickets.state` is a legacy copy of `tickets.status`. Three writers keep it in step (the mailroom
Ticket model, the API's `setTicketStatus`, and the seed), and exactly one reader depends on it:
the finance export `legacy/export/nightly-csv.js`, which runs from cron on mail-01, outside the
app and outside the test suite. The last attempt (#139) dropped the column and broke that export
(#142). FD-10 can drop the column only if the export keeps emitting a `state` column with the
value `resolved` by deriving it from `status`. Today the schema creates `state` on every new
database and the migration step never drops it from existing ones.

## Kind

missing-feature (a schema migration plus every writer and the one external reader).

## Root cause (with path:line evidence)

What exists today, and why each acceptance criterion fails on `main`:

**AC1 / AC2: the column exists, and nothing removes it.**

- `legacy/db/schema.sql:24` declares `state TEXT NOT NULL DEFAULT 'active'` inside
  `CREATE TABLE IF NOT EXISTS tickets`. A new database gets the column. On an existing database the
  statement does nothing, so editing the CREATE alone can never drop it (#139 hit this too; see
  `git show f5f94e0`).
- `legacy/db/connection.js:114-121`: `migrate()` only `exec`s `schema.sql`. There is no step that
  inspects or alters existing tables.
- Every startup path goes through that function: `apps/api/src/server.ts:13-18` calls
  `seedDatabase` for a new file (which calls `migrateLegacy()` at `apps/api/src/seed/seed.ts:16`),
  and calls `migrateLegacy()` directly for an existing one. `migrateLegacy` is
  `promisify(mailroom.db.migrate)` (`apps/api/src/legacy-adapter.ts:52`). The test helpers do the
  same (`apps/api/test/helpers.ts:23`, `legacy/test/helpers.js:8`). So the migration belongs in
  `legacy/db/connection.js` `migrate()`, on the mailroom's connection.
- Verified: on a throwaway DB, `migrate()` run twice still leaves
  `id,subject,customer_id,assignee_id,status,state,created_at,updated_at,closed_at`.
- The bundled SQLite (node:sqlite, `sqlite_version()` = 3.53.4) supports
  `ALTER TABLE tickets DROP COLUMN state`. I checked it against the real `schema.sql`, with the
  `sla_report` view present, both with and without `business_minutes` registered. Nothing indexes
  or views `state`: the index is on `status` (`legacy/db/schema.sql:30`), and the view reads
  `t.status` (`legacy/db/schema.sql:62`). #139's note about rebuilding the table applied to the
  old `sqlite3` driver and no longer holds (`legacy/db/connection.js:6-8`).

**AC3: the writers that would break once the column is gone.**

- `legacy/models/ticket.js:14-18,32,40`: `state` is in the model's column list, and `beforeSave`
  sets it. `defineModel` writes every listed column on INSERT and UPDATE
  (`legacy/lib/model.js:149-151,163-188`). With the column dropped, every `Ticket.create` (ingest,
  `legacy/ingest/ingest.js:79-90`) and every `Ticket.updateStatus` (rules via
  `legacy/rules/context.js:90-93`, such as reopen-on-reply) fails with `no such column: state`.
- `apps/api/src/tickets/tickets-repository.ts:101-116`: the API's `setTicketStatus` writes
  `state = ?` using its own `STATE_FOR_STATUS`.
- `apps/api/src/seed/seed.ts:3,63-75` writes `state = ?` with that same map.
- The web app never touches `state`. It changes status only through `PATCH /api/tickets/:id/status`
  (`apps/web/src/tickets/ticket-detail-page.tsx:40`, `apps/web/src/tickets/tickets-api.ts`). The
  contract has no ticket `state`: `packages/contract/openapi.yaml` only has the SLA `state`
  (`openapi.yaml:429-434`), which is a different thing. No contract change, so no regenerated
  `schema.d.ts`.

**AC4: the reader outside the app (the trap).**

- `legacy/export/nightly-csv.js:21-30,61-66,82` selects `t.state`, filters
  `WHERE t.state = 'resolved'`, and writes a `state` CSV column. The header comment at
  `nightly-csv.js:10-12` says finance matches on column names and state values.
- `ops/crontab:17-18` runs it at 02:15 from `/srv/front-desk`, separately from the app. It never
  calls `migrate()`.
- `docs/history/issues/142.md`: #139 dropped the column, and the export died with
  `no such column: t.state`. Finance's import keys on the `state` column and the value
  `resolved`. They agreed to change only "if you give us the new format in writing". FD-10 AC4
  ("keeps getting exactly what it gets now") means the CSV must not change at all: same header,
  same column order, `state` still `resolved`.
- Baseline CSV from `main` (one closed ticket, throwaway DB):
  ```
  ticket_id,customer_email,customer_name,subject,state,opened_at,resolved_at,business_minutes
  1,a@example.com,A,"Refund, please",resolved,2026-10-05T13:00:00.000Z,2026-10-05T15:00:00.000Z,120
  ```
- The other cron job, `legacy/bin/sweep-rules.js:15`, already filters on `status`. It only needs
  the Ticket model fix.

**Existing tests that assert on `state`:** `legacy/test/rules/apply-to.test.js:82-83` selects
`status, state` and expects `state: 'active'`. It will fail with `no such column` once the column
is dropped, so it must change to assert only `status`.

**Not affected:** the SLA cache (`legacy/lib/cache.js`, used by `legacy/lib/sla.js:182-196`)
snapshots `status`, `created_at` and `closed_at`. Dropping `state` changes none of those, so the
migration needs no cache invalidation. `Ticket.afterSave` (`legacy/models/ticket.js:44-49`) keeps
clearing it on mailroom writes.

## Implementation plan

1. **Failing tests first.** Add `legacy/test/migrate.test.js` and `legacy/test/export.test.js`
   (see "Failing test proposal"). Add `process.env.FINANCE_EXPORT_DIR = path.join(dir, 'exports');`
   to `legacy/test/setup.js`. `legacy/config.js:46` otherwise resolves it to `<cwd>/exports`,
   which is the real checkout.
   Check: `TZ=UTC npx vitest run --project legacy legacy/test/migrate.test.js legacy/test/export.test.js`.
   The migration test fails on its assertion. The export test passes on `main` and has to stay
   green.

2. **Schema.** Remove line 24 (`state ...`) from `legacy/db/schema.sql`. New databases are then
   created without the column.

3. **Migration (in `legacy/`, CommonJS and callbacks).** In `legacy/db/connection.js` `migrate()`,
   after `open().exec(sql)`, read `PRAGMA table_info(tickets)` and, only when it lists `state`, run
   `ALTER TABLE tickets DROP COLUMN state`. Do it inside the same `defer` so the callback contract
   stays the same. It must be safe to run twice (the column check makes it so), and it must run on
   the mailroom's connection (the view needs `business_minutes`). Keep it out of `schema.sql`,
   because `ALTER ... DROP COLUMN` fails on a second run. Optional: before dropping, log a count of
   rows where `state` disagrees with the mapping of `status` (see Risks).
   Check: `TZ=UTC npx vitest run --project legacy legacy/test/migrate.test.js`.

4. **Mailroom model.** In `legacy/models/ticket.js`, remove `'state'` from `columns`, the
   `STATE_FOR_STATUS` map (lines 9-18), and the `ticket.state = ...` line in `beforeSave` (line 40).
   Keep `afterSave`'s `cache.del('sla:' + ticket.id)` as it is.
   Check: `TZ=UTC npx vitest run --project legacy legacy/test/model.test.js legacy/test/ingest.test.js legacy/test/rules`.

5. **Finance export: keep the output identical.** In `legacy/export/nightly-csv.js`, derive the
   column from `status` instead of reading `t.state`. For example,
   `CASE t.status WHEN 'closed' THEN 'resolved' WHEN 'pending' THEN 'on_hold' ELSE 'active' END AS state`,
   with `WHERE t.status = 'closed' AND t.closed_at IS NOT NULL`. Leave `COLUMNS`, the column order,
   the file name and `row.state` unchanged. Update the header comment so it says `state` is now
   derived and still part of finance's format (reference #142 and FD-10). This query works whether
   or not the column has been dropped yet, which matters because cron can run it before the API
   restarts on mail-01.
   Check: `TZ=UTC npx vitest run --project legacy legacy/test/export.test.js`.

6. **API.** In `apps/api/src/tickets/tickets-repository.ts`, delete `STATE_FOR_STATUS`
   (lines 101-106) and change `setTicketStatus` to `SET status = ?, updated_at = ?, closed_at = ...`.
   Fix the parameter list to match: `(status, at, status, at, ticketId)`.
   Check: `TZ=UTC npx vitest run --project api apps/api/src/tickets`.

7. **Seed.** In `apps/api/src/seed/seed.ts`, drop the `STATE_FOR_STATUS` import (line 3) and the
   `state = ?` assignment and argument (lines 65, 69).
   Check: `TZ=UTC npx vitest run --project api apps/api/src/seed`.

8. **Existing test.** In `legacy/test/rules/apply-to.test.js:82-83`, select only `status` and expect
   `{ status: 'open' }`.
   Check: `TZ=UTC npx vitest run --project legacy legacy/test/rules/apply-to.test.js`.

9. **API-level guard (recommended).** In `apps/api/src/tickets/tickets.test.ts`, add a test that
   closes and reopens a ticket through `PATCH`, then reads
   `PRAGMA table_info(tickets)` / `SELECT status` with `desk.db`. Both the API and the mailroom
   connection are then known to work against the migrated table.
   Check: `TZ=UTC npx vitest run --project api apps/api/src/tickets/tickets.test.ts`.

10. **Docs.** Update the "Tickets: `status` and `state`" section of `CLAUDE.md` (lines 51-61),
    which is untracked and still a draft. Also update the comment in `legacy/models/ticket.js`.
    Record that the export derives `state` from `status`. Add a short note under
    `docs/history/issues/` or in the commit message that links #142.
    Leave `ops/crontab` unchanged.

11. **Full gate.** `npm run check`. `legacy/test/rules/assign-round-robin.test.js` is a known
    failure (FD-03) only in shuffled orders, and `check` uses the default order. Then
    `npm run feature:check -- FD-10` (left to the orchestrator; this triage did not run it).

## Failing test proposal

**Primary (fails on `main`):** `legacy/test/migrate.test.js`. It gets a fresh per-file database
from `legacy/test/setup.js`.

- Arrange a database as it exists in production today. Before calling `migrate()`, create
  `customers` and the current production `tickets` table, including
  `state TEXT NOT NULL DEFAULT 'active'`, with raw `run(...)` from `legacy/test/helpers.js`. Copy
  the DDL from `legacy/db/schema.sql` on `main`, so the test doesn't depend on the new schema.
  Insert three tickets: (`open`,`active`), (`pending`,`on_hold`) and (`closed`,`resolved`, with a
  `closed_at`).
- Act: `await migrate(); await migrate();`. The second call proves it is safe to run twice.
- Assert:
  `expect((await all('PRAGMA table_info(tickets)', [])).map(c => c.name)).not.toContain('state')`.
  Also assert that
  `await all('SELECT id, status, closed_at FROM tickets ORDER BY id', [])` still returns the three
  rows with statuses `open`, `pending` and `closed` and the original `closed_at`.
- Expected failure on `main`:
  `AssertionError: expected [ 'id', 'subject', 'customer_id', 'assignee_id', 'status', 'state', … ] not to include 'state'`.
  That is the right reason: `migrate()` only runs `CREATE TABLE IF NOT EXISTS` and never removes
  the column (AC1/AC2). It is not an import or syntax error. The row assertions pass on `main` and
  protect against data loss after the fix.

**Companion guard (passes on `main`, must stay green):** `legacy/test/export.test.js`. It needs
`FINANCE_EXPORT_DIR` set in `legacy/test/setup.js`. After `migrate()`, create a customer and a
ticket with the models, close it with `closed_at` on a fixed day such as `2026-10-05T15:00:00.000Z`,
and also add one open ticket and one pending ticket. Then call
`exportDay('2026-10-05', cb)` from `legacy/export/nightly-csv.js` and assert that the file is
exactly
`ticket_id,customer_email,customer_name,subject,state,opened_at,resolved_at,business_minutes\r\n1,...,resolved,...,120\r\n`,
with only the closed ticket present. This is AC4's contract with finance. Without this test, a
"fix" that just deletes `t.state` from the query would pass the migration test and repeat #142.

Command:
`TZ=UTC npx vitest run --project legacy legacy/test/migrate.test.js legacy/test/export.test.js`

## Risks

- **Repeating #142.** Grepping the TypeScript finds no reader, but `legacy/export/nightly-csv.js`
  reads `state` from cron (`ops/crontab:17-18`). The export must derive `state` from `status` and
  keep header, order and values byte-for-byte the same. Do not rename the column, and do not
  switch the values to `closed`.
- **Deploy order on mail-01.** Cron jobs run the checkout's code without migrating. The new export
  and the new Ticket model must work against both the old schema (column present) and the new one
  (column gone). The derived-CASE query and a model that doesn't list `state` both do. Old code
  against a migrated DB would break, so the code must be deployed before the API restarts.
  Restarting the API is what runs the migration.
- **Drift between `state` and `status`.** The export reads `state` today. Rows where the two
  disagree (for example from the #139 drop and #143 re-add on mail-01, if the column was re-added
  with `DEFAULT 'active'` and only partly backfilled) would make the derived export differ from
  today's. Before dropping, the migration could count
  `state <> CASE status WHEN 'open' THEN 'active' WHEN 'pending' THEN 'on_hold' ELSE 'resolved' END`
  and log it. Ops should run that query on mail-01 before deploying.
- **Migration has to run on the mailroom connection.** `sla_report` uses `business_minutes()`,
  which is registered only there (`legacy/db/connection.js:31`). DROP COLUMN worked in my test
  without it, but put the migration in `legacy/db/connection.js` anyway. The API must not run DDL
  on `tickets` from its own connection. That would also cross the legacy boundary, since
  `apps/api/src/database.ts` only applies the API-owned schema.
- **Must be safe to run twice.** `schema.sql` runs on every start. `DROP COLUMN` cannot go there
  and needs the `PRAGMA table_info` guard.
- **Config is read once.** `FINANCE_EXPORT_DIR` is read when `legacy/config.js` is first required
  (`legacy/config.js:46`). A test that sets it inside the test file after importing
  `helpers.js` (which requires `db/connection` → `config`) is too late, and the CSV would land in
  the repository's `exports/`. Set it in `legacy/test/setup.js`.
- **Concurrent connections.** The API process holds two connections to the same file. `DROP COLUMN`
  needs a write lock. Both connections set `busy_timeout = 5000`, and the migration runs at startup
  before the poller starts (`apps/api/src/server.ts:17-20`), so this should be fine. Prepared
  statements on the other connection are re-prepared automatically after the schema change.
- **Neighbouring rule, not in scope.** `setTicketStatus` (`tickets-repository.ts:108-116`) updates
  `status` and `closed_at` with plain SQL and does not clear the `sla:<id>` cache, contrary to
  CLAUDE.md. FD-10 only removes `state` from that statement, so it makes this neither better nor
  worse. If the implementer touches it anyway, the fix is a new `clearSlaCache(id)` wrapper in
  `legacy-adapter.ts` that calls `cache.del`, and never `closeLegacy()`.
- **Overlap with FD-06.** FD-06 adds a `priority` column to the same export. If both land, append
  `priority` after `business_minutes` and keep the derived `state`.
- **Known failure.** `legacy/test/rules/assign-round-robin.test.js` (FD-03) fails only in shuffled
  orders. Treat it as known if it shows up.

## Open questions for the user

1. Has finance moved off the `state` column (the Q3 change mentioned in #142)? Without that, the plan
   keeps the CSV identical, with `state` derived from `status`. If they have moved, AC4 could allow
   a format change, but only with their written sign-off.
2. Should the migration refuse to drop the column, or only log, when it finds rows where `state`
   and `status` disagree? Someone should first run the drift query on mail-01's database.
3. Is it acceptable to add `FINANCE_EXPORT_DIR` to `legacy/test/setup.js`? Test isolation needs it.
4. Should FD-10 also fix the missing SLA-cache clear in `setTicketStatus`, or leave it as a separate
   item?
