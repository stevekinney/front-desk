# FD-11: Merge duplicate tickets — triage plan

## Summary

Nothing about merging exists yet. There is no contract operation, no API route, no "merged" record in the schema, no web control, and the mailroom has no notion of a ticket that now lives elsewhere. `POST /api/tickets/1/merge` on main falls through to `unknownRoute` and returns `404 {"error":"No such route"}` (reproduced with a throwaway DB). Two existing mailroom behaviours also work against the spec: a reply that carries `[#<merged id>]` would thread onto the hidden shell, and a reply from a second address at the same company opens a new ticket because ingest only accepts mail from the ticket's own `customer_id` (reproduced: a reply from `orders@weissbakery.example` with `[#1]` on jonah's ticket created ticket #3). This item touches every layer: the contract, the API (the new route plus a merged-id guard on every existing per-ticket endpoint), the mailroom schema, mailroom ingest, the hourly sweep cron job, and the web app. Because the merged ticket's `status` is left alone and every write to a merged id is refused with 404, the finance export does not need to change.

## Kind

missing-feature (size L)

## Root cause (what is absent, with evidence)

Reproduction (throwaway `FRONT_DESK_DB`/`MAILROOM_INBOX`/`MAILROOM_LOCK` under `mktemp -d`, script in the session scratchpad, run with `npx tsx`):

```
merge 1 -> 2 404 {"error":"No such route"}
reply from orders@ with [#1] -> [{"filename":"zz-reply.json","ticketId":3,"created":true}]
```

### Contract and API

- `packages/contract/openapi.yaml:59-218` has no `/tickets/{ticketId}/merge` path and no `MergeInput` schema. `packages/contract/src/index.ts` exports no merge types.
- `apps/api/src/tickets/tickets-router.ts:26-79` has no merge route, so the request falls to `unknownRoute` (`apps/api/src/http.ts:39-41`, mounted at `apps/api/src/app.ts:24`). That is the 404 above.
- `apps/api/src/tickets/tickets-repository.ts:60-85` (`listTicketRecords`) has no way to hide a ticket. Every filter (`status`, `assigneeId`, `tag`) is optional, and with none set it returns every row (AC4).
- `apps/api/src/tickets/tickets-repository.ts:174-179` (`listMessages`) already orders by `m.created_at, m.id`. Once the messages are moved onto the survivor, AC3 ("oldest first") holds without extra code.
- `apps/api/src/tickets/tickets-repository.ts:108-124` shows the API writes `tickets` with plain SQL. `setTicketStatus` mirrors `state` (`STATE_FOR_STATUS`, :102-106) but does **not** clear the mailroom's SLA cache. A merge that copies that pattern for `created_at` would leave the survivor's SLA stale.

### Existing per-ticket endpoints would act on a hidden shell

Every per-ticket endpoint resolves its id through one of three lookups, none of which knows about merges:

| Endpoint                                      | Lookup                                       | Evidence                                                               |
| --------------------------------------------- | -------------------------------------------- | ---------------------------------------------------------------------- |
| `GET /tickets/:ticketId`                      | `findTicketRecord` via `loadTicket`          | `tickets-router.ts:29-33,41-46`; `tickets-repository.ts:87-91`         |
| `PATCH /tickets/:ticketId/status`             | `ticketExists`                               | `tickets-router.ts:48-54`; `tickets-repository.ts:93-95`               |
| `PUT /tickets/:ticketId/assignee`             | `ticketExists`                               | `tickets-router.ts:56-65`                                              |
| `PUT`/`DELETE /tickets/:ticketId/tags/:tagId` | `ticketExists`                               | `tags-router.ts:34-57` (guard at :55)                                  |
| `POST /tickets/:ticketId/replies`             | none in the API; `sendReply` → `Ticket.find` | `tickets-router.ts:67-76`; `legacy/outbox/mailer.js:31-34`             |
| `POST /tickets/:ticketId/canned-replies/:id`  | `findTemplateContext` (own SQL)              | `canned-replies-router.ts:34-49`; `canned-replies-repository.ts:43-59` |

Unguarded, a reply on a shell id records an outbound message on the hidden shell and queues mail to the shell's customer (`legacy/outbox/mailer.js:65`), and `PATCH status` on a shell writes `state='resolved'` plus `closed_at` (`tickets-repository.ts:108-116`), which puts the duplicate in the finance export (`legacy/export/nightly-csv.js:66`). Every one of these operations already declares a `404 NotFound` response in the contract (`packages/contract/openapi.yaml:71-72, 98-99, 126-127, 149-150, 171-172, 184-185, 217-218`), so refusing merged ids with 404 needs no contract change.

### SLA cache (AC7 trap)

- `legacy/lib/sla.js:182-193` (`forTicket`) caches a snapshot under `sla:<id>`. `dueAt` is computed from `created_at` (`legacy/lib/sla.js:135-143`) and reused until someone calls `cache.del`.
- `legacy/models/ticket.js:44-49`: only `Ticket.afterSave` clears it.
- `apps/api/src/legacy-adapter.ts:29` types `cache` as `{ clear(): void }` only, and `closeLegacy()` (:64-68) stops the poller and closes the DB. There is no per-ticket clear (`legacy/lib/cache.js:28-30` exports `del`).
- AC7 implies that when an older ticket is merged into a newer one, the survivor takes the older `created_at`. Otherwise the due time jumps later, which resets the customer's clock. That is an API-side write to `tickets.created_at`, so it has to clear `sla:<survivor>`.

### Mailroom ingest (AC9, AC11)

- `legacy/ingest/ingest.js:29-38` (`findThread`): In-Reply-To resolves through `messages.message_id` to `parent.ticket_id`. If the merge moves the messages, replies to either conversation's emails already land on the survivor.
- `legacy/ingest/ingest.js:44-48` (`findBySubject`): `[#123]` resolves with `Ticket.find(123)` and never follows a merge. A customer replying to an outbound email from the merged ticket (subject built by `legacy/outbox/mailer.js:22-25` as `Re: … [#<merged id>]`) would thread onto the hidden shell. With no In-Reply-To (`fixtures` JSON mail usually has none) the subject token is the only link.
- `legacy/ingest/ingest.js:76`: `if (existing && existing.customer_id === customer.id)`. Customers are keyed by exact email (`legacy/models/customer.js:22-37`). After a cross-address merge (AC9), a reply from the merged ticket's address does not match the survivor's `customer_id`, so a **new ticket** opens. Reproduced above. The guard exists on purpose: `legacy/test/ingest.test.js:122-139` ("opens a new ticket when someone else uses the token") must keep passing.

### Schema

- `legacy/db/schema.sql:19-29`: `tickets` has nothing that records a merge. Both schema files run on every start (`legacy/db/connection.js:114-121`, `apps/api/src/database.ts:13-18`), and SQLite has no `ADD COLUMN IF NOT EXISTS`, so adding a column means a guarded `ALTER` in JS. A new `CREATE TABLE IF NOT EXISTS` is idempotent as written (`legacy/db/schema.sql:1`: "Every statement must be safe to run more than once").
- On a fresh DB, `openDatabase` runs the API schema **before** `migrateLegacy()` (`apps/api/src/server.ts:11-17`, `apps/api/src/seed/seed.ts:16`). Anything that alters `tickets` therefore cannot live in `apps/api/src/db/schema.sql`.

### Cron jobs and the finance export

- `ops/crontab:15` runs `legacy/bin/sweep-rules.js` at minute 5 of every hour. It never migrates: `legacy/bin/sweep-rules.js:12-31` goes straight to its query, and `db.migrate` (`legacy/db/connection.js:114-121`) is only called by the API (`apps/api/src/server.ts:17`, `seed.ts:16`) and tests. Its query `SELECT id FROM tickets WHERE status <> 'closed'` (`sweep-rules.js:15`) would include hidden shells. `assign-round-robin` (`legacy/rules/assign-round-robin.js:15,26-28`) would spend a rotation slot assigning a hidden ticket, `escalate-vip` would tag it, and `auto-close-stale` (`legacy/rules/auto-close-stale.js:18-33`) would close a pending shell. Closing it writes `state='resolved'` and `closed_at`, which pushes a duplicate row into finance's file.
- Every rule run, from the sweep and from ingest (`legacy/ingest/ingest.js:129`), goes through `rules.applyTo` → `context.loadTicket` (`legacy/rules/index.js:55-64`, `legacy/rules/context.js:35-73`), which already returns early when the ticket row is missing (`index.js:58`). That is the single place to skip shells.
- If `loadTicket` references `ticket_merges` and cron runs before the table exists on mail-01, every `applyTo` errors, `sweep-rules.js:26-28` logs each one and carries on, and the script exits 0 having run no rules. Nobody watches `rules.log`. This is the same shape as issue #142 (`docs/history/issues/142.md`): a cron job on mail-01 that the test suite never exercised.
- `ops/crontab:18` runs `legacy/export/nightly-csv.js` nightly. It selects `state = 'resolved' AND closed_at IS NOT NULL` (`legacy/export/nightly-csv.js:61-67`, filter at :66) with a fixed column list (:21-30). Finance keys on the columns and on `state` values (#142). If the merge **closes** the merged ticket, the export gains a "resolved" row for a duplicate, with its own `business_minutes`. If the merge leaves the shell's `status`, `state` and `closed_at` alone and nothing else can write them afterwards, the export is unaffected, needs no change, and never references `ticket_merges`.

### Web

- `apps/web/src/tickets/ticket-detail-page.tsx:60-105`: the controls section has no merge input or button. `apps/web/src/tickets/tickets-api.ts:1-32` has no `mergeTicket`. The page uses `useApi` (`apps/web/src/use-api.ts`) keyed on `ticket:<id>`, so after a merge it must navigate to `/tickets/<into>`, which re-keys the load. `useApi` keeps the previous data visible while reloading (`use-api.ts:17-21`).
- The page already has a local `const merge = (updated: Ticket) => …` (`ticket-detail-page.tsx:35`, used at :40 and :69). The new handler must use a different name.
- A 404 renders `Could not load ticket #<id>: <error.message>` (`ticket-detail-page.tsx:23-32`), and `errorHandler` passes `HttpError.message` through as `error` (`apps/api/src/http.ts:43-48`). A specific 404 message for a merged id therefore reaches a stale `/tickets/<shell>` link with no web change.

## Implementation plan

### Approach (recommended design)

- **Record merges in a new mailroom table** in `legacy/db/schema.sql`:
  ```sql
  CREATE TABLE IF NOT EXISTS ticket_merges (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    ticket_id      INTEGER NOT NULL UNIQUE REFERENCES tickets (id),
    into_ticket_id INTEGER NOT NULL REFERENCES tickets (id),
    merged_at      TEXT NOT NULL
  );
  CREATE INDEX IF NOT EXISTS ticket_merges_into ON ticket_merges (into_ticket_id);
  ```
  It is idempotent with no JS migration, and the cron jobs can read it without the API. The `id` column lets `defineModel` (`legacy/lib/model.js:39,89,174` assumes `id`) back a one-line `legacy/models/ticket-merge.js`, so ingest reads it through a model (`TicketMerge.findOne({ ticket_id })`) as CLAUDE.md asks. The API writes it with plain SQL, as it already does for `tickets`. I rejected `tickets.merged_into_id` because it needs a `PRAGMA table_info`-guarded `ALTER` in `legacy/db/connection.js migrate()`, and it would break `Ticket.save` on any DB that hasn't been migrated if added to the model's `columns`.
- **Flatten chains when merging.** Rows whose `into_ticket_id` is the ticket being merged are repointed at the new survivor, so every lookup is a single hop.
- **Move, don't copy.** Repoint `messages.ticket_id` and `outbox.ticket_id` to the survivor. Move `ticket_tags` with `INSERT OR IGNORE … SELECT` and then delete the merged ticket's rows, so tag filters and FD-01 counts never see the shell.
- **Leave the merged ticket's `status`, `state` and `closed_at` untouched.** Finance sees nothing new, and the state/status mirror is not involved for the shell.
- **A merged id is gone from the API (404 everywhere).** `ticketExists` and `findTicketRecord` exclude ids listed in `ticket_merges`, so GET detail, PATCH status, PUT assignee, tag add/remove, and the merge route itself (either side already merged) all return 404 through their existing guards. POST replies gets an explicit `ticketExists` guard before `sendReply`, and `findTemplateContext` gets the same exclusion, so canned replies return 404 too. `loadTicket` uses `findMergeTarget` to make the 404 message say where the ticket went: `Ticket 5 was merged into #7`. This keeps the "finance sees nothing" invariant true after the merge, not just at the moment of merging. No contract change is needed for this (all of these operations already declare 404). Whether GET should instead return the survivor is a product call; see Open question 5.
- **Survivor:** `created_at = min(a.created_at, b.created_at)` (AC7). `updated_at = now()` so it sorts to the top. Assignee: keep the survivor's, and take the merged ticket's only if the survivor has none (AC6; Open question 2). Status stays unchanged (Open question 3). Subject stays unchanged (Open question 7). After the transaction, call `clearSlaCache(survivorId)` and `clearSlaCache(mergedId)`.
- **Do the whole merge in one synchronous transaction on the API connection** (`db.exec('BEGIN IMMEDIATE')` … `COMMIT`, `ROLLBACK` on throw). Nothing inside it may `await`, because the in-process mailroom shares the file through its own `DatabaseSync` connection (`legacy/db/connection.js:26-33`).
- **Customer rule (AC8/AC9):** allowed when `customer_id` matches, or when both addresses have exactly the same domain (the part after the last `@`; no subdomain matching, so `a@mail.acme.example` and `b@acme.example` do not match) and that domain is not a shared mailbox provider. Plus-addressing needs no special case: the same mailbox with a different `+tag` already shares a domain. The provider list is `example.com`, `gmail.com`, `yahoo.com`, `outlook.com`, `hotmail.com`, `icloud.com`, `me.com`, `aol.com`, `proton.me`. Otherwise the request is rejected with `400 {"error":"Only tickets from the same customer can be merged"}`. Keep the rule in exactly one function (`apps/api/src/tickets/same-customer.ts`). This is the working assumption; see Open question 1.
- **Mailroom threading:** (1) `findThread` passes whatever it finds, on both the In-Reply-To and the `[#id]` paths, through `resolveMerged`, which follows `ticket_merges` to the survivor. (2) Line 76 also accepts a sender who already has an inbound message on that thread (`Message.findOne({ ticket_id, from_email, direction: 'inbound' })`). After a merge, the moved messages make the merged-from address such a sender. This keeps `legacy/test/ingest.test.js:122` (a stranger using the token) green, and the mailroom needs no copy of the domain rule.
- **Rules skip shells in one place, and the sweep migrates first.** `context.loadTicket` adds `AND NOT EXISTS (SELECT 1 FROM ticket_merges mg WHERE mg.ticket_id = t.id)` to its existing query, so `applyTo` returns early for a shell (`legacy/rules/index.js:58`) whether it was reached from the sweep or from ingest. The sweep query itself is left alone. `sweep-rules.js` calls `db.migrate` before its query, so the table exists however the deploy is ordered. `migrate` only creates what is missing (`legacy/db/connection.js:109-121`), it is what the API already runs on every start, and it runs on the mailroom connection where `business_minutes()` (needed by the `sla_report` view) is registered (`connection.js:31`). This avoids a deploy-order rule that would have to live somewhere an operator might not read.
- **Outbound replies** keep going to the survivor's customer only (`legacy/outbox/mailer.js:65`). The merged-from address gets no copy. See Open question 8.

## Risks

- **Stale SLA badge on the survivor.** Any API write to the survivor's `created_at`, `status` or `closed_at` must call the new `clearSlaCache`. `setTicketStatus` (`tickets-repository.ts:108-116`) already lacks one, which is FD-04's problem, so don't copy that pattern.
- **Hidden shells reachable by cron.** Handled in step 8: the shell is skipped in `context.loadTicket`, and `sweep-rules.js` migrates before it queries, so there is no deploy-order constraint. If someone later adds a merge-aware query to `nightly-csv.js`, it must migrate first too (or not reference `ticket_merges`).
- **Finance export (#142).** Closing the merged ticket would add a "resolved" duplicate row to the 02:15 CSV. The merge leaves `status`/`state`/`closed_at` alone, and every API write to a shell 404s. If the survivor's status is ever changed by the merge, write `state` too.
- **New per-ticket endpoints.** The 404 guard lives in `ticketExists`/`findTicketRecord`/`findTemplateContext`. An endpoint added later (FD-04 pause, FD-05 create, FD-06 priority) that writes `tickets` with its own lookup would bypass it. Step 12's CLAUDE.md bullet records the rule.
- **Shared ingest behaviour.** Relaxing `ingest.js:76` changes who can thread onto a ticket. The "already wrote inbound on this thread" check must not let a stranger in. Keep `legacy/test/ingest.test.js:122` green.
- **Ingest/merge race (accepted).** `ingestNew` is several deferred steps (`legacy/ingest/ingest.js:72-120`, each `db` call is `setImmediate`-deferred, `legacy/db/connection.js:57-67`). If a merge commits after ingest has resolved `[#A]` to A but before its `Message.create`, that one message lands on the hidden shell. The window is a few event-loop turns in one process and merges are rare, so this plan accepts it. A later fix would be to have `listMessages` also read messages from tickets merged into the survivor.
- **Transaction across two connections.** Keep the merge transaction fully synchronous. An `await` inside `BEGIN IMMEDIATE` would block the in-process mailroom's sync connection until `busy_timeout` (5 s) and then `SQLITE_BUSY`.
- **Test isolation.** Legacy tests that touch merges must add `ticket_merges` to their `beforeEach` table cleanup. `tickets` uses AUTOINCREMENT, so ids don't repeat, but leftover rows still leak between tests in shuffled order.
- **Cross-item interactions.**
  - FD-01: tag counts must exclude shells; moving the tags handles this.
  - FD-04: a pause history on the merged ticket is dropped.
  - FD-05: `POST /api/tickets` shares the router.
  - FD-06: whose priority wins.
  - FD-07: `GET /api/reports/sla` and the `sla_report` view (`legacy/db/schema.sql:59-68`) will list shells unless filtered.
  - FD-10: drops `state`. The merge adds no new `state` writers.
- **The domain rule.** `example.com` hosts unrelated people in the seed and in every API test. A bare domain match would let teammates merge strangers' tickets. If the user decides `example.com` is a company domain, the AC8 test pair in step 6 must change.

## Open questions for the user

Each question has the assumption the plan currently uses. The plan is consistent with every assumption; changing one changes only the steps named.

1. **What counts as "the same company" (AC9), and which status rejects different customers (AC8)?** Assumption: exact same email domain, excluding the shared-provider list (which includes `example.com`); no subdomain matching; rejected with `400 {"error":"Only tickets from the same customer can be merged"}`. Alternatives: an explicit company on customers (new column and UI), a bare domain match, or `409` (the contract already has a Conflict response, `openapi.yaml:353`, used for tags at :249-250). Affects steps 4 and 6.
2. **Assignee (AC6).** Assumption: when both are assigned, the survivor keeps its own; when only the merged ticket is assigned, the survivor inherits it. Affects step 5.
3. **Survivor status.** Assumption: unchanged, even if the merged ticket was open and the survivor closed. Reopening would write `status`, `state` and `closed_at` and need `clearSlaCache`. Affects step 5.
4. **The merged ticket's own status and the finance export.** Assumption: left untouched, so finance sees nothing. Closing it would require the export to filter merged ids (and then `nightly-csv.js` would need to migrate first). Affects steps 5 and 9.
5. **What a merged ticket id does on the API.** Assumption: 404 on every per-ticket endpoint (GET detail, status, assignee, replies, tags, canned replies, merge), with GET's message naming the survivor (`Ticket 5 was merged into #7`), which the web page shows for a stale link. Alternative: `GET` returns the survivor (and the web page redirects to it). Writes would still 404 either way, because acting on a shell breaks the finance invariant. Affects steps 6 and 11.
6. **Already-merged tickets.** Assumption: merging a ticket that is already merged, or into one, returns 404 (it falls out of assumption 5). Alternatives: 400, or follow to the survivor. Affects step 6.
7. **Subject.** Assumption: the survivor's subject does not change.
8. **Outbound replies after a cross-address merge.** The spec covers inbound replies only (AC11). Assumption: replies go only to the survivor's customer address (`legacy/outbox/mailer.js:65`), so after merging jonah@'s ticket into orders@'s, jonah@ stops receiving replies. Alternative: CC every address that has written on the thread, which changes the mailroom's outbox. Affects nothing in the current plan.
9. **Confirmation and labels (AC1, AC12).** Assumption: the browser's `window.confirm` with `Merge #<id> into #<n>? This can't be undone.`, an input labelled `Merge into ticket #`, and a `Merge` button. Alternative: an in-page dialog. Affects step 11 and its tests.
