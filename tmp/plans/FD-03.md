## Summary

`legacy/test/rules/assign-round-robin.test.js` depends on the order its tests run in, because the
rule keeps its rotation counter at module scope and every test in the file shares one loaded copy
of the rule. CI shuffles tests inside each file (`--sequence.shuffle`), so the file fails in more
than half of CI's seeds while `npm test` (declaration order) passes. The fix is test-only: load a
fresh copy of the rule before each test, and have the two tests that inherited history set it up
themselves. Then remove the entry from `KNOWN_FAILURES.md`. The work happens in a fresh git
worktree, not the main checkout.

## Kind

`test-infrastructure`. Production behaviour is correct and must not change (spec criterion 4;
`tmp/PLAN.md` C2 and C3): the rule's counter is meant to carry over between calls in one process,
and `npm run rules:parity` plus `legacy/test/rules/golden.test.js` rely on that. The defect is that
the unit test file shares that state between tests. A reviewer who sees the module-level counter as
the bug could call this `bug`, but the approved plan keeps `legacy/rules/` unchanged.

## Root cause

Confirmed against the code at HEAD `bdaca5e` on 2026-10-06.

- `legacy/rules/assign-round-robin.js:8` declares `let next = 0;` at module scope.
- `legacy/rules/assign-round-robin.js:26-27` reads `ctx.teammates[next % ctx.teammates.length]`,
  then increments `next`. Spam (`:24`) and an empty roster (`:25`) return before the increment.
- `legacy/test/rules/assign-round-robin.test.js:6-7` loads the rule once through `createRequire`,
  so all six tests share one `next`.
- `legacy/test/rules/assign-round-robin.test.js:25` expects teammate 1 (assumes `next` is 0 on
  entry); `:31` expects teammate 2 (assumes 1); `:44-47` expect 3 then 1 (assumes 2). These are
  only right in declaration order.
- `scripts/test-order.ts:49` turns a seed into `--sequence.shuffle --sequence.seed=<n>`. Vitest
  shuffles tests inside a file as well as files, so the counter is usually wrong on entry.
- `.github/workflows/ci.yml:30` picks a random seed per job, and `scripts/check.ts:58` with
  `scripts/test-order.ts:23-27` shuffles whenever `TEST_SEED` is set. Locally, `npm test` and
  `npm run check` without a seed use declaration order (`scripts/check.ts:58`,
  `shuffleByDefault: false`), which is why laptops are green.
- `vitest.config.ts:26-34` does not override `pool` or `isolate`, so each test file gets its own
  module registry. Nothing leaks between files; the problem is entirely inside this one file.

| Test (declaration order)                     | Expects          | Counter value it assumes on entry |
| -------------------------------------------- | ---------------- | --------------------------------- |
| only looks at open tickets that nobody has   | `when` only      | n/a (never calls `run`)           |
| gives the first ticket to the first teammate | assign 1         | 0                                 |
| gives the next ticket to the next teammate   | assign 2         | 1                                 |
| leaves spam for the spam folder              | no effects       | n/a (spam returns before `next`)  |
| wraps around after the last teammate         | assign 3, then 1 | 2                                 |
| does nothing when nobody is on the desk      | no effects       | n/a (empty roster returns first)  |

Reproduced, all with `TZ=UTC`:

- File alone, seed 2 (re-run in Round 1, exit 1): `2 failed | 4 passed (6)`. "gives the next
  ticket…" got `[ { type: 'assign', teammateId: 3 } ]` instead of teammate 2; "wraps around…" got a
  different two-item sequence than `[3, 1]`.
- File alone, seeds 1–10: fails on 2, 3, 5, 7, 9, 10, matching `tmp/PLAN.md`.
- File alone, default order: `6 passed (6)`.
- Whole suite, seed 2: `2 failed | 104 passed (106)`, both failures in this file.
- Whole suite, seed 98848 (a CI seed): `2 failed | 104 passed (106)`, failing "gives the first
  ticket…" and "gives the next ticket…". The first test failing shows the mechanism is the shuffle
  inside the file, not leakage from other files.
- No shuffle (re-run in Round 1): running only "gives the next ticket to the next teammate" with
  `-t` gives `1 failed | 5 skipped (6)` with
  `expected [ { type: 'assign', teammateId: 1 } ] to deeply equal [ { type: 'assign', teammateId: 2 } ]`.
- A small node script confirmed the approved fix mechanism: after two calls (teammates 1, 2),
  `delete require.cache[path]` and a fresh `require` produce teammate 1 again. The rule has no
  `require`s of its own (`legacy/rules/assign-round-robin.js:1-30`), so evicting one cache entry is
  enough.

Other loaders of the rule, checked so the per-test reload can't disturb them:

- `legacy/test/rules/golden.test.js:9` loads `legacy/rules/index.js` (which requires the rule at
  `legacy/rules/index.js:25`) in its own file, so it keeps its own copy. Its fixture cases rely on
  the counter carrying over within that one test.
- `legacy/test/rules/apply-to.test.js:8` also loads the rules through `index.js`, in its own file,
  and only asserts that an assignee is set (`apply-to.test.js:68-69`), so it is order-independent.
- `scripts/rules-parity.ts:63,166` loads the rule once per process with its own `createRequire`.

## Risks

- **Cache eviction only resets this module.** `delete require.cache[rulePath]` works because the
  rule has no `require`s. If FD-08 (the TypeScript port) or anything else gives the rule a
  dependency that holds state, the reset would need to evict that too.
- **`require` here is Node's, not Vitest's.** The file uses `createRequire`, so `require.cache` is
  Node's CommonJS cache, which Vitest does not manage. Switching the test to `import` would break
  the reset; keep `createRequire`.
- **File isolation is load-bearing.** If someone sets `isolate: false` or a shared pool in
  `vitest.config.ts`, the per-test reload in this file would also reset the copy other legacy test
  files see. Today `vitest.config.ts:26-34` keeps the default. D4 and D5 test the per-file
  `require.cache` behaviour empirically.
- **`beforeEach` must cover the `when`-only test.** `rule` is undefined until `beforeEach` runs;
  putting the hook first inside `describe` covers all six tests.
- **Formatting (Round 1).** `prettier --check .` (`scripts/check.ts:64`) fails in the main checkout
  today on untracked files unrelated to FD-03 (see "Where the work runs"). That is why the work
  moves to a worktree. In the worktree only the two hand-edited files can introduce a format
  failure; `features.json` is in `.prettierignore:9`.
- **Running `npm run check` in the main checkout gives a misleading red.** Anyone verifying from
  the main checkout will see `format` fail on `.claude/launch.json` and other plans. Report that as
  unrelated, not as an FD-03 failure.
- **Traps named in the brief, checked and not touched by this change:**
  - `tickets.status`/`tickets.state` mirror (`docs/history/issues/142.md`,
    `legacy/export/nightly-csv.js`, `ops/crontab` 02:15 job): no ticket writes; the round-robin
    rule only calls `ctx.assign`.
  - SLA cache in `legacy/lib/cache.js`: assignment does not change `status`, `created_at` or
    `closed_at`.
  - `legacy/config.js` read once at require time: the reloaded module is only the rule, which reads
    no config. `legacy/test/setup.js` already sets the throwaway paths.
  - `apps/api/src/legacy-adapter.ts` boundary: no API code changes.
  - `docs/history/issues/97.md` (mailroom lock): not affected; the test never starts the poller,
    and the worktree has its own `MAILROOM_LOCK` anyway.
