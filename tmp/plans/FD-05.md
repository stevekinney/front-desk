# FD-05: Create a ticket from the web — triage plan

## Summary

Teammates can't open a ticket for a customer from the web app. Nothing in any layer supports it: the contract has no `POST /tickets`, the API has no route (on main `POST /api/tickets` falls through to `unknownRoute` and returns `404 {"error":"No such route"}`), the mailroom only creates tickets from inbox mail, and the inbox page has no "New ticket" control. The fix is a vertical slice: contract, then a mailroom function (so the Ticket model's hooks set `state` and clear the SLA cache), then an adapter wrapper, an API route and zod schema, and finally a web form and route.

## Kind

missing-feature

## Root cause (what is absent, with evidence)

Reproduced on main with a throwaway DB (`FRONT_DESK_DB`, `MAILROOM_INBOX` and `MAILROOM_LOCK` under `mktemp -d`, `MAILROOM_RULES=off`): `POST /api/tickets` with a valid body returned `404 {"error":"No such route"}` and `SELECT count(*) FROM tickets` stayed at 0.

**Contract**

- `packages/contract/openapi.yaml:29-57` has only `get: listTickets` under `/tickets`. There is no `post` and no input schema such as `NewTicketInput`.
- `packages/contract/src/index.ts:1-27` has no alias for an input type.
- `packages/contract/src/generated/schema.d.ts` must be regenerated. `scripts/check.ts:33-58` fails if it drifts from the YAML.

**API**

- `apps/api/src/tickets/tickets-router.ts:35-76` has `GET /tickets`, `GET /tickets/:id`, `PATCH .../status`, `PUT .../assignee` and `POST .../replies`, but no `POST /tickets`. Unmatched routes reach `unknownRoute` (`apps/api/src/http.ts:39-41`, registered at `apps/api/src/app.ts:24`) and return a 404.
- `apps/api/src/tickets/tickets-schemas.ts:1-26` has no create-ticket schema.
- The response shape for AC2 is `TicketDetail`, the same as `GET /tickets/:id` builds at `tickets-router.ts:41-46`: `loadTicket` and `withSla`, plus `listMessages`.

**Mailroom (`legacy/`), the only code that creates tickets today**

- `legacy/ingest/ingest.js:71-121`: `ingestNew` creates the ticket and message through models (`Customer.findOrCreate`, `Ticket.create`, `Message.create`). It is tied to a `ParsedMail` and to threading, and `afterIngest` (`ingest.js:127-133`) runs the automation rules.
- `legacy/models/customer.js:22-37`: `Customer.findOrCreate` lowercases and trims the email before an exact-match `findOne`. Every customer the mailroom wrote is stored in lowercase, so this gives case-insensitive matching (AC4). The customer's name is filled in only when the existing customer has none.
- `legacy/models/ticket.js:37-49`: `beforeSave` sets `state` from `status` (open→active) and stamps `created_at` from `clock`. `afterSave` runs `cache.del('sla:' + id)`. Creating through this model satisfies the status/state mirror (#142) and the SLA-cache rule with no extra code.
- `legacy/index.js:24-40` exports no create-ticket entry point, so there's nothing to wrap yet.
- `apps/api/src/legacy-adapter.ts:26-46`: the `LegacyMailroom` interface has no create-ticket member, and no wrapper exists (`:51-94`).

**Web**

- `apps/web/src/tickets/inbox-page.tsx:62-73`: the list header holds only `<SimulateMailButton>`. There is no "New ticket" control.
- `apps/web/src/tickets/tickets-api.ts:1-32` has no `createTicket`.
- `apps/web/src/app.tsx:23-32`: routes are only `/` and `tickets/:ticketId`.
- `apps/web/test/mock-api.ts:44` always answers with status 200. A web test for AC5 (400 keeps the form open) needs the mock to support a non-200 status.

**Traps checked**

- **Automation rules would break "unassigned" (AC3).** With rules on (production default, `legacy/config.js:43`), `assign-round-robin` (`legacy/rules/assign-round-robin.js:14-28`) assigns every open, unassigned ticket, and `escalate-vip` (`legacy/rules/escalate-vip.js`) assigns VIPs. So the implementation must not create the ticket by writing an inbox file and polling (as `desk.receive` in `apps/api/test/helpers.ts:35-50` does), and must not call `afterIngest`/`rules.applyTo`. The tests run with `MAILROOM_RULES=off` (`apps/api/test/setup.ts:16`), so a test would not catch this. Separately, the hourly sweep (`legacy/bin/sweep-rules.js:15-30`, `ops/crontab:15`) will round-robin-assign any still-unassigned open ticket within the hour, as it already does for mail. That is existing behavior, not something FD-05 must prevent. See Open questions.
- **status/state (#142, `docs/history/issues/142.md`).** Create through `Ticket.create` so `beforeSave` writes `state='active'`. A raw `INSERT` from the API would get `state` only from the column default (`legacy/db/schema.sql:24`), which works but is fragile. FD-10 later drops `state`, so keep all writes in the model.
- **SLA cache (`legacy/lib/cache.js`, `legacy/lib/sla.js:183-196`).** `forTicket` memoizes a snapshot per id. A brand-new AUTOINCREMENT id can't have a stale entry, but going through `Ticket.create` runs `afterSave` and clears it anyway. No new `del` wrapper is needed for this feature. (The adapter's lack of a per-ticket clear is relevant to `setTicketStatus`, `tickets-repository.ts:108-116`, which updates status with raw SQL and never clears `sla:<id>`. That gap already exists and is out of scope here.)
- **Finance export (`legacy/export/nightly-csv.js:59-101`, `ops/crontab:18`).** It only reads `state='resolved' AND closed_at IS NOT NULL`. A new open ticket has `state='active'`, so the export is unaffected until the ticket is closed through existing paths.
- **Config is read once (`legacy/config.js:6-8`).** No new env vars are needed. Tests use the existing setup files, and the legacy test for the new function must keep `legacy/test/setup.js` loading first (it does, via `setupFiles`).
- **Adapter boundary (CLAUDE.md, `docs/architecture.md`).** Only `apps/api/src/legacy-adapter.ts` may import `legacy/`. Add the legacy function to `legacy/index.js` and a promisified, typed wrapper in the adapter.
- **`business_minutes()` / `sla_report`.** Don't query it from the API connection. Use `withSla` → `getSla` (the mailroom connection) as the existing routes do.
- **Two SQLite connections.** The mailroom writes the rows on its connection, and the API reads them on its own (`apps/api/src/database.ts:13-19`, WAL). This already works for `sendReply` → `findMessage` (`tickets-router.ts:73-75`), so read the ticket only after the adapter promise resolves.
- **Atomicity.** The mailroom has no transactions: customer → ticket → message are three separate writes. Validation must run entirely in zod before any write so that a 400 "creates nothing" (AC5). A mid-chain DB error could still leave an orphan customer or a ticket with no message, the same as `ingestNew`. That's acceptable but worth noting.
- **`messages.message_id` is UNIQUE (`legacy/db/schema.sql:40`).** NULL is allowed and repeats freely in SQLite. You can leave it null, or generate `<fd-web-<ticketId>-…@frontdesk.example>` like `legacy/outbox/mailer.js:49-56` does. Either way it never collides with real mail.

## Implementation plan

1. **Contract.** In `packages/contract/openapi.yaml`, add `post: createTicket` under `/tickets` with `requestBody` `$ref: '#/components/schemas/NewTicketInput'` (required `customerEmail`, `subject`, `body`; optional `customerName`, all strings, `customerEmail` with `format: email`). Responses: `'201'` → `TicketDetail`, `'400'` → `BadRequest`. Add the `NewTicketInput` schema under `components.schemas`. Export `export type NewTicketInput = Schemas['NewTicketInput'];` from `packages/contract/src/index.ts`. Run `npm run generate` and commit `packages/contract/src/generated/schema.d.ts`.
   - Check: `npm run generate && npm run typecheck -w @front-desk/contract`, then `git diff --stat packages/contract`.

2. **Mailroom function.** Create `legacy/tickets/open-ticket.js` (CommonJS, callbacks, JSDoc types, short header comment explaining why: teammates open tickets for walk-ins and phone calls; no mail and no rules). Signature: `openTicket({ customerEmail, customerName, subject, body }, cb)`. Steps:
   - `Customer.findOrCreate({ email: customerEmail, name: customerName || null }, ...)`
   - `Ticket.create({ subject, customer_id, status: 'open', assignee_id: null, created_at: clock.isoNow() }, ...)`
   - `Message.create({ ticket_id, direction: 'inbound', from_name: customer.name, from_email: customer.email, body, message_id: null or a generated fd-web id, sent_at: <same isoNow> }, ...)`
   - `cb(null, { ticket, message, customer })`.

   Do NOT call `rules.applyTo`. Export it from `legacy/index.js` as `tickets: { openTicket: openTicket }`.
   - Check: add `legacy/test/open-ticket.test.js`. It should cover: freeze `clock` at a fixed weekday instant and assert `created_at` equals it; `state` is `active` and `assignee_id` is null; an existing `Ana@Example.com` customer is reused for `ANA@example.com`; one inbound message. Then reset `clock.freeze(null)` in `afterEach`. Run `TZ=UTC npx vitest run --project legacy legacy/test/open-ticket.test.js`.

3. **Adapter.** In `apps/api/src/legacy-adapter.ts`, extend `LegacyMailroom` with `tickets: { openTicket(input: {...}, cb: Callback<{ ticket: { id: number } }>): void }`. Add `export async function openTicket(input): Promise<number>`, which resolves with the new ticket id.
   - Check: `npm run typecheck`.

4. **API schema and route.**
   - In `apps/api/src/tickets/tickets-schemas.ts`, add `newTicketSchema = z.object({ customerEmail: z.string().trim().pipe(z.email('Enter a valid email address')), customerName: z.string().trim().max(200).optional().transform(v => v || undefined), subject: z.string().trim().min(1, 'Subject is required').max(200), body: z.string().trim().min(1, 'Message is required').max(10_000) })`. Use the zod 4 API (`zod@4.6.5` is installed). Confirm the exact email helper compiles.
   - In `tickets-router.ts`, add `router.post('/tickets', ...)`: `parse(newTicketSchema, req.body)` → `await openTicket(input)` → `const ticket = await loadTicket(id)` → `res.status(201).json({ ...ticket, messages: listMessages(db, id) } satisfies TicketDetail)`.
   - Register it before `/tickets/:ticketId` routes. Ordering doesn't actually matter, because the methods differ.
   - Check: `TZ=UTC npx vitest run --project api apps/api/src/tickets/tickets.test.ts`.

5. **API tests** in `apps/api/src/tickets/tickets.test.ts`, new `describe('POST /api/tickets')`:

## Failing test proposal

Location: `apps/api/src/tickets/tickets.test.ts` (new `describe('POST /api/tickets')` block, reusing the file's `desk`).

```ts
describe('POST /api/tickets', () => {
  it('creates an open, unassigned ticket with the customer message', async () => {
    const before = Date.now();
    const res = await request(desk.app)
      .post('/api/tickets')
      .send({
        customerEmail: 'walkin@example.com',
        customerName: 'Wren Walker',
        subject: 'Phoned in: reprint',
        body: 'Customer called asking for a reprint of order 4411.',
      })
      .expect(201);

    const detail = res.body as TicketDetail;
    expect(detail).toMatchObject({
      subject: 'Phoned in: reprint',
      status: 'open',
      assignee: null,
      customer: { name: 'Wren Walker', email: 'walkin@example.com' },
      messageCount: 1,
      closedAt: null,
    });
    expect(Date.parse(detail.createdAt)).toBeGreaterThanOrEqual(before - 1000);
    expect(detail.sla.remainingMinutes).toBeGreaterThan(0);
    expect(detail.messages).toHaveLength(1);
    expect(detail.messages[0]).toMatchObject({
      direction: 'inbound',
      fromEmail: 'walkin@example.com',
      body: 'Customer called asking for a reprint of order 4411.',
      delivery: null,
    });
    const row = desk.db
      .prepare('SELECT status, state FROM tickets WHERE id = ?')
      .get(detail.id) as { status: string; state: string };
    expect(row).toEqual({ status: 'open', state: 'active' });
  });
});
```

It only imports `TicketDetail`, which already exists, so it compiles on main.

- Command: `TZ=UTC npx vitest run --project api apps/api/src/tickets/tickets.test.ts -t "POST /api/tickets"`
- Expected failure on main: supertest's `.expect(201)` throws `Error: expected 201 "Created", got 404 "Not Found"`. That is because no `POST /tickets` route exists: the request falls through to `unknownRoute` (`apps/api/src/http.ts:39-41`) and returns `{"error":"No such route"}`, which I reproduced. This is exactly the gap the spec describes. It is an assertion failure, not an import or syntax error. After the fix, the `state` assertion also guards the #142 mirror.

## Risks

- Creating the ticket by dropping an inbox file and polling, or by reusing `ingest`/`afterIngest`, runs the automation rules in production. `assign-round-robin` would then assign the ticket and break AC3, and API tests won't notice because they set `MAILROOM_RULES=off`. Use a dedicated mailroom function that skips the rules.
- Inserting the rows with raw SQL from the API would skip `Ticket.beforeSave`/`afterSave`. `state` would come only from the column default, `created_at` would come from the API's `new Date()` instead of the mailroom `clock`, and it would break the "the mailroom creates every ticket" invariant (`legacy/README.md`) and the boundary rule.
- Case-insensitive matching depends on stored emails being lowercase, which `Customer.findOrCreate` guarantees for every path that exists today. If anything ever inserts a mixed-case email, the exact-match lookup would miss and the UNIQUE constraint would still allow a near-duplicate. A `lower(email)` lookup is a safer variant, but it means a raw query in a model helper.
- Return `TicketDetail`, not bare `Ticket`. AC2 says "the same shape `GET /api/tickets/{id}` uses", and `TicketDetail` is a superset, so it satisfies either reading.
- AC5 requires that nothing is created on a 400. All validation, including trimming whitespace-only subject and body, must happen in zod before calling the adapter. The mailroom chain is not transactional.
- The web form must not let native HTML validation (`required`, `type=email`) silently block submission in tests that expect the API's 400 to be surfaced. jsdom does enforce constraint validation on `requestSubmit`/click submit.
- `apps/web/test/mock-api.ts` can't return non-200 today. Changing it touches every web test, so keep it backward compatible.
- Schema changes: none are needed. Don't touch `legacy/db/schema.sql` or `apps/api/src/db/schema.sql`.
- The contract-drift step in `npm run check` fails if `schema.d.ts` isn't regenerated after editing the YAML.
- Interactions with other backlog items: FD-08 (port rules to TS) and FD-09 (auto-tag incoming mail) apply to mail. A web-created ticket is not mail, so keep it out of those paths. FD-10 (drop `state`) will remove the mirror, and keeping the write in `Ticket.beforeSave` means there's one place to change. FD-04/FD-07 change SLA math, and the new ticket uses `getSla` like every other ticket.
- `clock.freeze` in a legacy test is module-level state. Reset it in `afterEach`, because CI shuffles the test order.

## Open questions for the user

1. Should any automation rules run on web-created tickets, for example `tag-billing` or `escalate-vip` (VIP → `urgent` tag and assignment to the lead)? The spec says "open and unassigned", so the plan runs none. Note that the hourly `sweep-rules.js` will still round-robin-assign it within the hour, as it does for email tickets.
2. Should the inbound message record which teammate created it? For example, `author_id` set to the current teammate, which would need `teammateId` in the request body. The spec's body has no teammate field, so the plan leaves `author_id` null.
3. When an existing customer has no name and the form supplies one, should it fill in the name? `Customer.findOrCreate` does this today. When the customer already has a different name, the plan keeps the existing name.
4. Should the "New ticket" form be its own route (`/tickets/new`) or a dialog on the inbox? Either meets AC1. The plan suggests a route for simplicity.
