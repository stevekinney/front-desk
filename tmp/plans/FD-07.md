# FD-07: Business-hours settings drive the SLA (triage plan)

## Summary

The desk's hours, time zone and SLA length are fixed in `legacy/config.js`. Nothing lets anyone read or change them over HTTP, nothing stores them, there is no SLA report endpoint, and there is no Settings page. The SLA code also captures the time zone once, when it is first required, and caches each ticket's due time, so changing the values at runtime would not reach tickets that were already read. Criterion 4 also exposes two bugs in the existing math. The desk's day counts the 17:00 hour, so it is nine business hours long instead of eight. And the code steps through time in whole UTC hours, so it miscounts in zones with a half-hour offset, which the new "any valid IANA zone" setting would allow.

## Kind

missing-feature, with two latent SLA-math bugs that criterion 4 makes visible.

## Root cause (with path:line evidence)

What is missing:

- **No settings store.** The SLA values are a literal object: `legacy/config.js:51-57` (`hours: 8, openHour: 9, closeHour: 17, timeZone: 'America/New_York'`). Like the rest of the file, it is read once at require time (`legacy/config.js:5-8`). No table holds them: `legacy/db/schema.sql` and `apps/api/src/db/schema.sql` have none.
- **No HTTP surface.** `apps/api/src/app.ts:19-23` mounts tickets, tags, canned replies, teammates and mail. There is no settings router and no reports router. Unknown paths fall through to `unknownRoute`, which returns 404 (`apps/api/src/http.ts:39-41`).
- **No contract.** `packages/contract/openapi.yaml` has no `/settings/...` or `/reports/...` paths. `packages/contract/src/index.ts` exports no settings or report types.
- **No adapter wrappers.** `apps/api/src/legacy-adapter.ts:26-46` exposes `sla.forTicket` only (line 30). It has no access to the settings or to report data, and no clock.
- **No web UI.** The header in `apps/web/src/app.tsx:10-15` contains only the brand link and the teammate switcher. The routes at `apps/web/src/app.tsx:23-31` have no settings page.

Why runtime changes would not reach the SLA even with a store (criterion 3):

1. `legacy/lib/sla.js:20-25` creates `wallClockFormat` with `config.sla.timeZone` when the module loads. Changing the zone afterwards has no effect.
2. `legacy/lib/sla.js:136` reads `config.sla.hours`, and `legacy/lib/sla.js:55` reads `openHour` and `closeHour`, from the literal config object.
3. `legacy/lib/sla.js:182-194` caches `snapshot()` under `sla:<id>`, including the computed `dueAt` (`legacy/lib/sla.js:135-143`). Only `Ticket.afterSave` evicts that entry (`legacy/models/ticket.js:44-49`), so after a settings change every ticket that was already read keeps its old due time. `legacy/lib/cache.js` has `del` and `clear` but no way to list keys (`legacy/lib/cache.js:14-37`). `cache.set` is called only at `legacy/lib/sla.js:191`, so `sla:` is the only key prefix in use.
4. `businessMinutesBetween` is synchronous, and it also runs inside the SQLite user function `business_minutes()`, which is registered `deterministic: true` on the mailroom's connection only (`legacy/db/connection.js:31,43-48`). Settings must therefore be available synchronously in the mailroom process. An async lookup inside the math is not possible.

Bugs in the current math (criterion 4):

- **The 17:00 hour counts as a business hour.** `legacy/lib/sla.js:54-56` is `hour >= openHour && hour <= closeHour`, and its comment says "9 to 5, inclusive". Reproduced with throwaway mailroom paths: `businessMinutesBetween(Mon 2026-10-05 09:00 NY, Tue 09:00 NY)` returns **540**, but the spec says 480. A ticket arriving Monday at 16:00 NY gets a due time of Tuesday 15:00 NY (`2026-10-06T19:00:00Z`) instead of Tuesday 16:00 (`20:00Z`). The existing test at `legacy/test/sla.test.js:123-131` passes only because a ticket that arrives at 09:00 uses up its eight hours before 17:00.
- **The code assumes whole-hour offsets.** `legacy/lib/sla.js:58-66` (`startOfNextHour`) steps on UTC hour boundaries, and `isOpenAt` checks only the start of each step. Reproduced on main (Node v26.9.0, throwaway `FRONT_DESK_DB`/`MAILROOM_INBOX`/`MAILROOM_LOCK`, `config.sla.timeZone` set to `Asia/Kolkata` before `sla.js` loads): Monday 08:30 to 17:00 IST counts **450** (should be 480), and 08:30 to 18:00 IST counts **510** (should be 480; the `< closeHour` fix alone would make it 480 by accident, so it does not discriminate). Criterion 2 accepts any valid IANA zone, so the math has to handle this. The 08:30 to 17:00 case is the one to test.

Other places that bake in the settings:

- `legacy/export/nightly-csv.js:32-37` creates `dayFormat` with `config.sla.timeZone` at require time. The CSV's `business_minutes` column comes from the `sla_report` view (`legacy/export/nightly-csv.js:60-67`, `legacy/db/schema.sql:59-69`). The view calls `business_minutes()`, which will use whatever settings are in memory in that process. The export runs as its own process from cron at 02:15 on a box set to America/New_York (`ops/crontab:6,17-18`), and its default day is `deskDay(Date.now() - 24h)`, computed at `legacy/export/nightly-csv.js:111` before `exportDay` runs at line 112. See Open question 1 for what the export does under this plan.
- `apps/web/src/tickets/sla-badge.tsx:3-7` assumes a 480-minute business day when it formats "2d 1h".

Traps checked:

- **status/state mirror (issue #142).** FD-07 writes no ticket status in production code, so the mirror is unaffected. Leave `state` alone, along with `nightly-csv.js`'s columns and its `state = 'resolved'` filter (`docs/history/issues/142.md`). Finance's import keys on this file and asked for format changes "in writing" (`docs/history/issues/142.md:46-47`).
- **`sla_report` view.** It may be queried only on the mailroom's connection (CLAUDE.md). The view also uses SQLite's `strftime('now')` (`legacy/db/schema.sql:66`), not `legacy/lib/clock.js`, so a test cannot freeze its "now".
- **Configuration is read once.** Keep `config.sla` as the defaults only. Don't try to change runtime behavior through `process.env`.
- **Adapter boundary.** Only `apps/api/src/legacy-adapter.ts` may import from `legacy/`. Never call `closeLegacy()` to clear the cache (`apps/api/src/legacy-adapter.ts:64-68`), because it also stops the poller and closes the database.
- **Out of scope here: `PATCH /tickets/:id/status`.** It writes status with plain SQL and does not evict `sla:<id>` (`apps/api/src/tickets/tickets-repository.ts:107-115`). FD-04 owns that problem, but don't make it worse.

   Check: `npm run generate && git diff --stat packages/contract`, then `npm run typecheck`.

2. **Mailroom table.** In `legacy/db/schema.sql`, add a single-row table that is safe to run twice. Because it uses `IF NOT EXISTS` and `INSERT OR IGNORE`, existing databases need no migration, and a second run never overwrites saved values.

   ```sql
   CREATE TABLE IF NOT EXISTS business_hours (
     id INTEGER PRIMARY KEY CHECK (id = 1),
     open_hour INTEGER NOT NULL, close_hour INTEGER NOT NULL,
     time_zone TEXT NOT NULL, sla_hours INTEGER NOT NULL, updated_at TEXT NOT NULL);
   INSERT OR IGNORE INTO business_hours (id, open_hour, close_hour, time_zone, sla_hours, updated_at)
     VALUES (1, 9, 17, 'America/New_York', 8, strftime('%Y-%m-%dT%H:%M:%fZ', 'now'));
   ```

   The mailroom owns the table because it owns the SLA clock, and its cron jobs read the mailroom's tables without the API running.
   Check: the "migrating again keeps saved values" case in step 3's `legacy/test/business-hours.test.js`, and the "survives a restart" case in step 7. (`legacy/test/model.test.js:12-14` migrates only once, so it does not prove this.)

3. **Mailroom cache, model and settings module.** Use CommonJS and callbacks.
   - `legacy/lib/cache.js`: add `delPrefix(prefix)`, which deletes every key that starts with `prefix`. Use `cache.delPrefix('sla:')` for settings changes rather than `cache.clear()`, so a future cache key is not wiped by accident.
   - `legacy/lib/business-hours.js` (requires the model at the top):
     - `defaults()` returns `{ openHour: config.sla.openHour, closeHour: config.sla.closeHour, timeZone: config.sla.timeZone, slaHours: config.sla.hours }`.
     - `current()` returns the in-memory settings synchronously. It starts as `defaults()`.
     - `remember(row)` turns a `business_hours` row into settings, ignores a row that would be unusable (hours outside 0..24, `open_hour >= close_hour`, `sla_hours < 1`, or a zone `Intl.DateTimeFormat` rejects) by keeping the defaults, replaces the in-memory copy, and calls `cache.delPrefix('sla:')` when the values differ from the previous copy.
     - `load(cb)` reads row 1 through the model (`BusinessHours.find(1, ...)`), calls `remember`, and calls back with `current()`. If the table is missing (a database that was never migrated: the error message contains `no such table`) or row 1 is missing, it uses `defaults()` without writing anything; `migrate` re-inserts row 1 on the next startup. Any other error goes to `cb`.
     - `save(settings, cb)` finds row 1, sets the four columns and saves it through the model. If row 1 is missing, it creates the record instead (the table is then empty, so SQLite assigns id 1, which the `CHECK` allows). It calls back with `current()`.
   - `legacy/models/business-hours.js`: `defineModel({ table: 'business_hours', columns: ['open_hour', 'close_hour', 'time_zone', 'sla_hours', 'updated_at'] })`. `beforeSave` stamps `updated_at` with `clock.isoNow()`. `afterSave` calls `require('../lib/business-hours').remember(record)` and then `cb(null)`. The require goes inside the function, not at the top, because the settings module requires the model; follow the precedent and comment at `legacy/db/connection.js:45-46`.
   - Export from `legacy/index.js:24-40` as `businessHours: businessHours`, and add `BusinessHours` to `models`.
     Check: a new `legacy/test/business-hours.test.js` (call `migrate()` in `beforeAll`) with these cases: `load` returns the defaults; `save` then `load` returns the new values; `save` evicts a pre-set `sla:<id>` entry but keeps a pre-set non-`sla:` key; `migrate()` a second time after `save`, then `load`, still returns the saved values; a row written directly with `db.run('UPDATE business_hours ...')` (as another process would) is picked up by the next `load` and evicts `sla:<id>`. Restore the defaults with `save` in `afterEach`, since CI shuffles test order.

4. **SLA math (`legacy/lib/sla.js`).**
   - Give `businessMinutesBetween(start, end, settings)` and `addBusinessMinutes(start, minutes, settings)` an optional third argument. When it is omitted they use `businessHours.current()`. The SQL function `business_minutes()` keeps calling with two arguments (`legacy/db/connection.js:43-48`), so the view uses the in-memory settings. Tests pass settings explicitly, so no test has to change the global settings to try another zone.
   - Remove the module-level `wallClockFormat` and memoize one `Intl.DateTimeFormat` per zone in a `Map`.
   - Change `isBusinessHour` to `hour >= openHour && hour < closeHour` (criterion 4), and fix its comment.
   - Replace `startOfNextHour` with `startOfNextQuarterHour`: `(Math.floor(ms / QUARTER) + 1) * QUARTER`, where `QUARTER` is 15 minutes. Every current zone's offset from UTC is a multiple of 15 minutes, so every local hour boundary, including DST changes, falls on a UTC quarter hour. Replace the "whole number of hours" comment accordingly.
   - `snapshot(ticket)` uses `current().slaHours * 60`.
   - `forTicket` calls `businessHours.load` first, then reads the cache. `load` evicts `sla:*` when the stored row differs from memory, so a settings write from another process is picked up on the next read without a fingerprint on each snapshot.
   - Add `report(cb)`: call `businessHours.load`, then `db.all('SELECT id, status, created_at, closed_at FROM tickets ORDER BY id', [], ...)` and map each row to `{ ticketId: id, status, businessMinutes: businessMinutesBetween(new Date(created_at), closed_at ? new Date(closed_at) : clock.now()) }`. A closed ticket with a null `closed_at` counts to now, matching the view's `coalesce` (`legacy/db/schema.sql:66`) and `summarize` (`legacy/lib/sla.js:153`); both writers stamp `closed_at` on close (`legacy/models/ticket.js:70`, `apps/api/src/tickets/tickets-repository.ts:110-112`), so it should not occur. Compute in JS so legacy tests can freeze "now"; don't query the view from the API connection.

## Risks

- **Stale SLA cache.** If the settings save path doesn't evict `sla:*`, tickets that were already read keep their old `dueAt`. That breaks criterion 3, and only for tickets read before the change, so it is easy to miss in a test that creates a fresh ticket after the PUT. Never use `closeLegacy()` to clear the cache.
- **The time zone captured at require time.** `legacy/lib/sla.js:20-25` builds a formatter when the module loads. Changing `openHour` would appear to work while the zone silently stays America/New_York. (`legacy/export/nightly-csv.js:32-37` does the same on purpose under this plan.)
- **Finance sees changed numbers.** Even pinned to the defaults, the `< closeHour` fix lowers the CSV's `business_minutes` by 60 for each business day a resolved ticket spanned past 17:00. Finance asked for changes "in writing" (`docs/history/issues/142.md:46-47`), so the user must announce this before it ships (Open question 1).
- **The export and the API report can disagree.** Once someone saves non-default settings, `GET /api/reports/sla` follows them and the CSV does not. That is the stated assumption; flip it only with the user's answer.
- **Settings shared across tests.** Within one test file the database and the mailroom's in-memory settings are shared, so a PUT in one test changes the SLA in the next, and CI shuffles test order. Restore the defaults in `afterEach`. Pure math tests pass settings explicitly instead.
- **Extra reads.** `forTicket` now runs one small `SELECT` on `business_hours` per call. The ticket list calls it per ticket (`apps/api/src/tickets/with-sla.ts`). Acceptable at this desk's size.
- **The SLA definition changes for every ticket.** Because of the `< closeHour` fix, seeded and closed tickets near the boundary may switch between met and missed. That is what the spec asks for.
- **The old badge format.** `apps/web/src/tickets/sla-badge.tsx:3-7` still assumes an 8-hour day for its "Nd" display (Open question 2). Existing web tests pin it (`apps/web/src/tickets/sla-badge.test.tsx:11`).
- **Infinite loops.** `addBusinessMinutes` never ends if no hour is ever open. Validation prevents that over HTTP, and `remember` keeps the defaults for an unusable row, such as a database edited by hand.
- **Overlap with other backlog items.** FD-04 (pausing on pending) edits the same `sla.js` functions, and FD-10 removes `state`. Expect merge conflicts in `legacy/lib/sla.js`.

## Open questions for the user

1. **The nightly finance export (blocking before ship, not before implementation).** (a) Should `deskDay` (`legacy/export/nightly-csv.js:32-46`), which picks the day a resolved ticket is filed under, follow the saved time zone or stay on America/New_York? (b) Should the CSV's `business_minutes` follow the saved hours or stay on the defaults? (c) Will you tell finance, in writing, that `business_minutes` drops by 60 per business day spanned past 17:00 because of criterion 4?
   **Assumption the plan uses:** (a) and (b) both stay on the defaults in `config.sla`; the export ignores saved settings (step 5). Reasons: the job runs unattended from cron at 02:15 on a New York box (`ops/crontab:6,17-18`) and files "yesterday" by `Date.now() - 24h` (`legacy/export/nightly-csv.js:111`). For a saved zone west of New York, that day has not ended at 02:15 New York time, so late closures would be missed; and changing the zone would re-file days, skipping or duplicating tickets across files that finance uses for month-end. Keeping `business_minutes` on the defaults means the feed changes only through code that can be announced once, not whenever someone saves the Settings page. For (c), the plan assumes you will announce it; the code change does not wait for that, but the deploy should.
2. **Badge day length.** Should the web badge's "d" unit (`apps/web/src/tickets/sla-badge.tsx:3-7`) use the configured day length (`closeHour - openHour` hours)? **Assumption:** no; it stays at 8 hours (480 minutes) and the badge is unchanged, so `sla-badge.test.tsx:11` still pins `480 -> '1d'`.
3. **Time-zone validation and storage.** **Assumption:** "a valid IANA zone" (`specs/FD-07.md:18`) means any name `Intl.DateTimeFormat` accepts, minus offset strings, stored exactly as typed. So `America/New_York`, `Europe/London`, `Asia/Kolkata`, `UTC`, `US/Eastern` and `EST` (all in the IANA database, some as backward links) are accepted, `america/new_york` is accepted and echoed back in lower case, and `+05:00` and `Mars/Olympus` are rejected. Say if you want lower-case input rejected, or old links such as `EST` refused.
4. **Report "now".** **Assumption:** `GET /api/reports/sla` computes in JS with the mailroom clock (`legacy/lib/clock.js`), which tests can freeze, rather than reading the `sla_report` view, which uses SQLite's real time.
