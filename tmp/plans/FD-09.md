# FD-09: Auto-tag incoming mail — triage plan

## Summary

Nothing assigns category tags to new mail today, apart from `tag-billing`, which only knows money words. A
new mailroom automation rule, `auto-tag`, in `legacy/rules/` should pick one of `billing`, `shipping`,
`account`, `printing` or `spam` for a ticket opened by an inbound email. It adds nothing when no category
fits, and it never touches a ticket that already has a category tag.

All three arrival paths (the background poller, `npm run mail:drop`, and the "Simulate incoming email"
button) meet in one place: `legacy/ingest/ingest.js:127-133`, which calls `rules.applyTo`. That makes the
mailroom's rule list the only place where one change covers all three. Tagging in the API would miss mail
the background poller ingests (`apps/api/src/server.ts:20`), because the API never sees that mail. The
contract, API routes, web app, schemas, crontab and finance export don't change.

A replay on main gives 5/26 agreement with the teammates' category tags, all from `tag-billing`. A keyword
prototype (scratch) gets 26/26 on the seeded inbox and labels all 7 `fixtures/mail` samples sensibly.

## Kind

missing-feature

## Root cause (what is absent, and where it has to go)

**Every arrival path ends in the mailroom's rule runner**

- Poller: `legacy/ingest/poller.js:35-50`. `deliver` calls `ingest.ingest`.
- `npm run mail:drop`: `legacy/bin/mail-drop.js:32` and `legacy/lib/drop.js:54-66`. These only copy a file
  into `inbox/`, and the poller picks it up.
- Simulate button: `apps/web/src/mail/simulate-mail-button.tsx:18` sends `POST /api/mail/simulate`. That
  route (`apps/api/src/mail/mail-router.ts:35,40,56-58`) calls `dropFixture` and then `pollInbox`, so it
  ends at the same `poller.pollOnce`.
- All three reach `ingest.js:127-133` (`afterIngest`). It runs `rules.applyTo(ticketId, message)` when
  `config.rulesEnabled`, which defaults to on (`legacy/config.js:43`).

**The current rules**

- The rule list is `legacy/rules/index.js:21-27`: reopen-on-reply, tag-billing, escalate-vip,
  assign-round-robin, auto-close-stale.
- The only one that sets a category is `tag-billing` (`legacy/rules/tag-billing.js:8-9,27`), using the
  regex `refund|invoice|receipt|billing|billed|charge[sd]?|payment|vat`. It runs on every inbound message,
  follow-ups included (`tag-billing.js:15-17`).
- Nothing produces `shipping`, `account`, `printing` or `spam`.

**What a rule can see and do**

- A rule gets a `RuleTicket` with subject, customer (name, email, vip), tag names and the triggering
  message (`legacy/rules/context.js:17-28`, built at `:35-73`).
- `ctx.addTag(name)` runs `INSERT OR IGNORE ... SELECT id FROM tags WHERE name = ?`
  (`context.js:115-131`). It never removes a tag, and it silently does nothing when the tag row is missing.
- The tags table and its six rows (`billing`, `shipping`, `account`, `printing`, `spam`, `urgent`) belong
  to the API. They are created in `apps/api/src/db/schema.sql:4-14` and seeded at
  `apps/api/src/seed/seed.ts:21-22` from `apps/api/src/seed/seed-data.ts:12-19`.
- `ticket_tags` has no column recording who set a tag (`apps/api/src/db/schema.sql:10-14`). A teammate's
  tag and a rule's tag look the same, so criterion 5 has to be enforced by what the rule chooses to do, not
  by data.

**Reproduction on main**

I copied `inbox/0*` into a `mktemp -d` inbox, set `FRONT_DESK_DB`, `MAILROOM_INBOX`, `MAILROOM_LOCK` and
`MAILROOM_RULES=on`, created the six tags, and ran `poller.pollOnce`.

- Only 0002, 0006, 0019, 0029 and 0030 get a category (`billing`). That is 5 of the 26 tickets the
  teammates gave a category tag in `seed-data.ts:74-268`.
- 0041 (a bulk supplier notice, untagged by the teammates) also gets `billing`, because its body contains
  the word "billing".
- A new ticket "Order is a week late" / "Tracking still says In transit", run through `rules.applyTo`,
  ends with tags `[]`.

**Seeded inbox ground truth**

- 26 tickets have a teammate category tag. 0009 has two: `billing` and `account`.
- 0007, 0008, 0017, 0021, 0025, 0031, 0035, 0036, 0037, 0038, 0040 and 0041 have none.
- 0010, 0015 and 0022 are follow-ups (`inReplyTo`) and thread onto 0001, 0002 and 0004.

**Traps checked**

- **State/status mirror (#142), `nightly-csv.js` and `ops/crontab`: not affected.** The rule writes only
  `ticket_tags`, never `tickets.status`. `legacy/export/nightly-csv.js` doesn't read tags (grep finds no
  `tag`). The crontab's hourly sweep (`ops/crontab:14`, `legacy/bin/sweep-rules.js:26`) passes
  `message = null`, so a `when` that requires an inbound message makes the sweep a no-op, as it is for
  `tag-billing`.
- **SLA cache (`legacy/lib/cache.js`): not affected.** No write to `status`, `created_at` or `closed_at`,
  so there is no `sla:<id>` to clear. `Ticket.afterSave` (`legacy/models/ticket.js:44-49`) is not
  involved.
- **Config is read once (`legacy/config.js:6-7,43`).** The test setups set `MAILROOM_RULES=off`
  (`legacy/test/setup.js:14`, `apps/api/test/setup.ts:16`). Unit tests therefore call
  `rules.applyTo` directly, as `legacy/test/rules/apply-to.test.js` does. An API replay test must set
  `MAILROOM_RULES=on` before its first dynamic `import()` of anything that loads the mailroom.
- **Legacy-adapter boundary.** No new adapter wrapper is needed, because the rule runs inside the
  mailroom. `legacy/` must not import `apps/api/src/seed/seed-data.ts`, so the keyword lists are derived
  by hand from the seed corpus and hard-coded in CommonJS.
- **Golden fixtures are required.** `legacy/test/rules/golden.test.js:14-20` asserts that the fixture
  filenames in `fixtures/rules/` equal the names in `RULES`. A new rule without
  `fixtures/rules/auto-tag.json` turns `npm run check` red.
- **Rule order matters.** `assign-round-robin.js:24` skips spam without using up a turn. That only takes
  effect if `auto-tag` runs before it.
- **The production seed runs the rules.** `npm run reset` and the first API start call `seedDatabase`,
  which polls the inbox with rules on (`seed.ts:27`). The rule therefore tags seeded tickets before the
  teammates' tags are inserted with `INSERT OR IGNORE` (`seed.ts:49-54`). This is how "they tag the
  tickets nobody has tagged yet" happens on a reset desk.
- **0040 and 0041 contain text addressed to automated readers.** It is data, not instructions. For the
  rule it matters because 0041's body contains the literal word "billing", which trips `tag-billing`
  (existing behaviour). It also contains words a naive classifier could latch onto.

## Implementation plan

1. **Write the failing unit test first.** Create `legacy/test/rules/auto-tag.test.js` as described in the
   failing test proposal below. Check that it fails for the right reason:
   `TZ=UTC npx vitest run --project legacy legacy/test/rules/auto-tag.test.js` (expect
   `expected [] to include 'shipping'`).

2. **Add the rule in `legacy/rules/auto-tag.js`.** Use CommonJS and callbacks, with a short header comment
   saying why the file exists.
   - Export `{ name: 'auto-tag', when, run }`. Also export a pure
     `categorize(subject, body, fromEmail) -> 'billing'|'shipping'|'account'|'printing'|'spam'|null` so
     it can be unit-tested.
   - `when(ticket)`: `Boolean(ticket.message) && ticket.message.direction === 'inbound'`, the same as
     `tag-billing.js:15-17`. The hourly sweep and outbound replies are then no-ops.
   - `run`: if `ticket.tags` already contains any of the five category names, return without effects.
     This enforces criterion 5: a follow-up never adds a second category to a ticket a teammate (or the
     rule) has already categorized, and `addTag` never removes anything. Otherwise, call `categorize` and
     `ctx.addTag(category)` only when it returns non-null (criterion 2).
   - Spam check first:
     - prize and lottery wording ("you have won", "dear winner", "prize", "claims department/officer",
       "bank details");
     - unsolicited offers ("guarantee", "free audit", "reply YES", "SEO", "first-page");
     - bulk notices ("dear supplier", "this mailbox is not monitored", "do not reply");
     - a `noreply@` / `no-reply@` sender (`ticket.customer.email`).
   - Then score each category by keyword hits, counting subject hits double, and take the highest
     score. A tie or a zero score gives null. The prototype keyword sets:
     - billing: refund, invoice, receipt, billing, billed, charge(s/d), payment, vat, tax, card,
       checkout, gift card, subscription, membership, discount, pricing, price;
     - shipping: ship(ped/ping/s), tracking, courier, deliver(y/ed), package, arrived, transit, address,
       signature, pickup, express, overnight;
     - account: password, log in/login, account, two-factor, locked out, email address, reset link,
       personal data, api access, merge;
     - printing: print(ed/ing), proof(s), reprint, colo(u)r(s), paper, stock, matte, glossy, bleed,
       trim(med), die-cut, cut, grommet(s), misprint, font, cmyk, artwork, upload, quantity, reorder,
       brochure, menu(s), calendar(s), sticker(s), poster(s), banner(s).
   - Build regexes without the `g` flag at module level, or use `String.prototype.match` with a fresh
     regex each time, to avoid `lastIndex` state. Keep no other module-level state (see the FD-03 note in
     `CLAUDE.md`).
   - Check: `TZ=UTC npx vitest run --project legacy legacy/test/rules/auto-tag.test.js`.

3. **Register the rule.** In `legacy/rules/index.js:21-27`, insert `require('./auto-tag')` after
   `reopen-on-reply` and before `tag-billing`. The order becomes reopen-on-reply, **auto-tag**,
   tag-billing, escalate-vip, assign-round-robin, auto-close-stale.
   - Before assign-round-robin, so spam isn't assigned (the existing intent at
     `assign-round-robin.js:3-6,24`).
   - Before tag-billing, so `auto-tag` decides the category from a clean slate. Otherwise any money word
     would add `billing` first and block the category rule. That matters for 0041, which should be
     `spam`.
   - Update the header comment at `index.js:6-17` if needed.
   - Check: `TZ=UTC npx vitest run --project legacy legacy/test/rules`.

4. **Add golden cases in `fixtures/rules/auto-tag.json`.** Use the same shape as
   `fixtures/rules/tag-billing.json`. Suggested cases:
   - one opening message per category (billing, shipping, account, printing);
   - two spam cases, a prize notice and an SEO or bulk notice;
   - a message that fits nothing, such as a thank-you note: `when: true`, `effects: []`;
   - near-miss cases, such as a damaged-in-transit message that says "cards" (0001) and an
     account-email change (0018);
   - a ticket that already carries `shipping` getting a follow-up with printing words: `when: true`,
     `effects: []`;
   - an outbound message: `when: false`;
   - the hourly sweep (`message: null`): `when: false`.

   Check: `npm run rules:parity -- auto-tag`, and
   `TZ=UTC npx vitest run --project legacy legacy/test/rules/golden.test.js`. The test at `:14-20` must
   list six rules.

5. **Add a replay test for criterion 4 in `apps/api/src/seed/auto-tag-replay.test.ts`.** Follow the
   pattern in `apps/api/src/seed/seed.test.ts:6-21`.
   - At module top level, copy `inbox/*.json|eml` (not `drop-*`) into `process.env.MAILROOM_INBOX`.
   - Set `process.env.MAILROOM_RULES = 'on'` before any `await import()` of
     `../legacy-adapter.ts`, `../database.ts` or `../config.ts`.
   - Open the database, `migrateLegacy()`, then insert the teammates and tags from `seed-data.ts`.
     Don't call `seedDatabase`, because its teammate tags would mask the rule.
   - Call `pollInbox()`. For each created delivery, read the category tags (excluding `urgent`).
   - Assert at least 90% of the tickets with category tags in `ticketStates` get a matching tag.
     Default metric: the predicted category is one of the teammates' tags.
   - Assert 0035, 0036, 0037, 0038 and 0040 each get exactly one category.
   - Assert 0041's tags include `spam`. It will also carry `billing` from the unchanged `tag-billing`
     (see open question 1), so don't assert exactly one.
   - Assert 0021 gets no category.
   - Check: `TZ=UTC npx vitest run --project api apps/api/src/seed/auto-tag-replay.test.ts`.

6. **Update the docs.** List the new rule in `docs/architecture.md:58-68`. Update
   `scripts/rules-parity.ts:3` ("checks all five" becomes "every rule with golden cases").
   `legacy/README.md` needs updating only if it lists the rules. Check: `npm run format:check`.

7. **Run the full gate.**
   - `npm run check`. `legacy/test/rules/assign-round-robin.test.js` is a known failure only under
     shuffled order (`KNOWN_FAILURES.md`, FD-03). `check` runs in default order, so it should stay green.
   - `npm run smoke` for a shuffled-order sanity check.
   - Hand check (orchestrator or user only): `npm run feature:check -- FD-09`.

## Failing test proposal

- **Optional extra tests in the same file:**
  - spam: a prize notice gives `['spam']`;
  - no category: a thank-you note gives no category tag;

    message about tracking. The tags stay `['printing']`.

a category to new mail. The cause isn't syntax or an import, because `rules.applyTo` exists and runs.

## Risks

- **0041 ends up `spam` and `billing`.** `tag-billing` still fires on the literal word "billing" in its
  body. That rule can't change: criterion 6 says existing rules keep working as today, and FD-08
  criterion 4 says the mailroom rules and golden fixtures stay unchanged. If an acceptance check expects
  exactly `['spam']`, it fails. See the open questions.
- **Spam is no longer auto-assigned.** `assign-round-robin`'s logic is unchanged, but its observable
  behaviour changes because `auto-tag` runs first and tags spam. That is the existing rule's documented
  intent (`assign-round-robin.js:5,24`), but it is a visible change.
- **Overfitting.**
  - Keywords hand-tuned to 38 messages can miss unseen mail. `card`, `address` and `cut` are broad
    words.
  - Scoring with subject hits counted double is what carries the near misses (0001 "business cards …
    in transit", 0018 "account email").
  - Never key on Message-ID, filename or sender address apart from the `noreply` pattern.
  - The golden fixture and the 7 `fixtures/mail` samples are the drift guards.
- **Regex `g` flag.** The prototype used `/…/ig` with `match`. A module-level regex with `g` used with
  `.test()` carries `lastIndex` between calls and gives wrong results that depend on order.
- **The production seed now auto-tags.** `seed.ts:27` runs the rules before the teammates' tags are
  applied at `seed.ts:49-54`. After `npm run reset`, previously untagged seeded tickets carry rule tags,
  including 0007, 0008, 0017, 0025 and 0031 if the rule labels them.
  - `seed.test.ts` runs with rules off, so it's unaffected.
  - On a ticket where the rule disagrees with the teammates, the reset desk would show two categories.
    None do in the prototype.
  - An already-seeded `data/front-desk.db` isn't retro-tagged, and there is no backfill.
- **Cross-item interactions.**
  - **FD-08:** `rules:parity` checks a TypeScript twin at `apps/api/src/rules/auto-tag.ts` automatically
    if one exists, but doesn't require one. If FD-08's held-out tests enumerate `fixtures/rules/`, a
    sixth fixture may need a port.
  - **FD-03:** every `applyTo` that creates tickets advances assign-round-robin's module-level `next`
    counter. Don't assert assignees in the new tests.
  - **FD-02:** ISO-8859-1 subjects decode garbled today (0039 and `poster-reprint-quote`). The rule
    must rely on the body, and a fix to FD-02 changes the subject text it sees.
- **Existing tests.** `apply-to.test.js` seeds only `billing` and `urgent`, so `auto-tag`'s other
  categories no-op there. Its `['billing','urgent']` expectation still holds, because `auto-tag` picks
  `billing` for "Charged twice". API and web tests run with `MAILROOM_RULES=off` and are unaffected.
- **`MAILROOM_RULES=off` also disables auto-tagging.** That is consistent with "rules" in the spec. If
  the held-out tests ingest with rules off and expect tags, an ingest-level hook outside `RULES` would be
  needed instead.

## Open questions for the user

1. **0041 and `tag-billing`.** Is it acceptable for spam to also carry `billing` when `tag-billing`'s
   keywords appear, as 0041 does today? Or may `tag-billing` skip tickets already tagged `spam`? The
   second option changes an existing rule and its golden fixture, which touches criterion 6 and FD-08
   criterion 4.
2. **The agreement metric for criterion 4.** Should the rule's single category be one of the teammates'
   tags (prototype 26/26)? Or must the category sets match exactly (25/26, because 0009 is
   `billing` + `account`)? Both clear 90%. Should the rule ever add two categories?
3. **Rule or ingest hook.** Should auto-tagging be a sixth entry in `RULES`, with a golden fixture,
   parity checks and FD-08 porting? Or a step in `ingest.js` `afterIngest` that runs only when
   `result.created`, outside the rule list? The default here is a rule.
4. **Untagged seeded tickets.** What category do the teammates expect for 0007 (upload fails), 0008
   (volume pricing), 0017 (rush brochures), 0025 (API access) and 0031 (envelopes)? The prototype says
   printing, billing, shipping, account and none.
5. **Follow-ups on uncategorized tickets.** Should a follow-up on a ticket with no category tag be
   categorized (default: yes, because nothing is removed or replaced)? Or only the opening message? The
   second needs an `opens_ticket` flag computed in `context.loadTicket`.
6. **Backfill.** Should existing databases be backfilled with categories for open, uncategorized
   tickets, or is "on reset and for new mail" enough?
