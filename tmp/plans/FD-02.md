# FD-02: Latin-1 subjects are garbled

## Summary

Raw `.eml` mail whose `Subject` or `From` display name uses RFC 2047 encoded words labelled
`ISO-8859-1` is decoded as UTF-8, so every accented byte (0x80-0xFF) becomes U+FFFD. The vendored
parser captures the charset label and then ignores it. The fix is legacy-only: transcode
ISO-8859-1 encoded words to UTF-8 before handing the message to `mailparse-lite` (the repo's
stated preference over a vendored patch), and cover it with a `legacy` unit test that uses the
existing `poster-reprint-quote` fixture.

## Kind

Bug.

## Root cause (with path:line evidence)

- `vendor/mailparse-lite/index.js:8` captures the charset as group 1 of `ENCODED_WORD`
  (`/=\?([^?]+)\?([BbQq])\?([^?]*)\?=/g`).
- `vendor/mailparse-lite/index.js:50-52`: `decodeWords` receives `charset` in the replacer but
  never uses it. Every word is decoded with `bytes.toString('utf8')`. In Latin-1, `é` is the single
  byte 0xE9 and `É` is 0xC9. On their own, neither is valid UTF-8, so each becomes U+FFFD.
- `vendor/mailparse-lite/index.js:121` sends the subject through `decodeWords`, and
  `index.js:56-58` (`parseAddress`) sends `From` through it too. That covers both AC1 and AC2.
- `legacy/ingest/parse.js:54-66` (`fromEml`) copies `mail.subject` and `mail.from.name` straight
  through. `legacy/ingest/ingest.js:81` stores the subject in `tickets.subject`, and
  `ingest.js:102` stores the name in `messages.from_name`. `legacy/models/customer.js:35` stores
  the name in `customers.name`. That column is read by `apps/api/src/tickets/tickets-repository.ts:29`
  and by canned replies at `apps/api/src/canned-replies/canned-replies-repository.ts:50`.
- I reproduced it on main by calling `parseFile` with throwaway `FRONT_DESK_DB`, `MAILROOM_INBOX`
  and `MAILROOM_LOCK` paths:
  - `fixtures/mail/poster-reprint-quote.eml` gives subject `"Devis pour une r�impression d'affiches"`
    and name `"Ren�e Dub�"`.
  - `inbox/0039-business-card-proofs-delivery.eml` gives `"�preuves des cartes de visite : d�lai de livraison?"`.
  - An inline sample (`=?iso-8859-1?b?yXByZXV2ZXM=?=`, lowercase label, B encoding, mixed with
    plain text and folded) also gives U+FFFD: `"Re: �preuves et d�lai ok"`.
  - The UTF-8 `inbox/0037-cafe-menu-proofs.eml` decodes correctly, which is the AC3 baseline.
- Folding and mixed plain text already work. `index.js:18` unfolds continuation lines, and patch 1
  at `index.js:47-49` drops the whitespace between adjacent encoded words. The fixture's subject is
  folded across two lines (`fixtures/mail/poster-reprint-quote.eml:3-4`) and joins correctly apart
  from the charset. The only defect is that the charset is ignored.
- Ticket #36 is `inbox/0039-business-card-proofs-delivery.eml`. There are 39 inbox files, and 3 of
  them are replies that thread onto earlier tickets (`0010`, `0015`, `0022`), so the 39th file opens
  ticket #36. Its seed state is at `apps/api/src/seed/seed-data.ts:260`.
- `PATCHES.md` (vendor/mailparse-lite/PATCHES.md, section "Before adding a patch") says to prefer
  fixing input in the mailroom, before or after `parse` in `legacy/ingest/parse.js`, and to patch
  the vendored copy only when that isn't possible. Here it is possible: the encoded words are plain
  ASCII in the header block, so they can be rewritten before parsing.

## Implementation plan

1. **Write the failing tests first** in `legacy/test/ingest.test.js`, next to the existing UTF-8
   `.eml` case at lines 62-75 (see "Failing test proposal" below).
   Check: `TZ=UTC npx vitest run --project legacy test/ingest.test.js -t "ISO-8859-1"`. On main
   both new cases should fail on their `toBe` assertions.

2. **Transcode ISO-8859-1 encoded words in the mailroom** in `legacy/ingest/parse.js`. Use
   CommonJS and no promises, as the legacy rules require.
   - Add a small function, for example `latin1WordsToUtf8(raw)`, that:
     - converts the buffer with `raw.toString('utf8')`. `mailparse-lite` does exactly this at
       `index.js:115`, so behavior stays the same;
     - splits off the header block at the first `/\r?\n\r?\n/` and leaves the body alone;
     - replaces each `/=\?(iso-8859-1)\?([BQ])\?([^?]*)\?=/gi` match in the header block. For B,
       the bytes are `Buffer.from(text, 'base64')`. For Q, `_` becomes 0x20 and `=XX` becomes a
       hex byte, mirroring `qDecodeBytes` at `index.js:29-43`. Each match is re-emitted as
       `'=?UTF-8?B?' + Buffer.from(bytes.toString('latin1'), 'utf8').toString('base64') + '?='`.
   - In `fromEml` (`parse.js:54-55`), call `mailparse.parse(latin1WordsToUtf8(raw))`.
     `mailparse.parse` accepts a string (`index.js:115`).
   - Why this is safe:
     - Latin-1 is one byte per character, so each word can be transcoded on its own.
     - The output is still a run of encoded words, so patch 1's joining across folds still applies.
     - UTF-8 and ASCII words never match the `iso-8859-1` label, so they pass through unchanged
       (AC3).
     - The `i` flag makes the label match case-insensitive (AC1).
     - It covers `Subject` and `From` together, because both are decoded from the same rewritten
       header block (AC2).
   - Update the header comment in `parse.js` with one line on why Latin-1 words are transcoded,
     pointing at PATCHES.md's guidance.
     Check: the step 1 command now passes. Also run
     `TZ=UTC npx vitest run --project legacy test/ingest.test.js` to confirm that "ingests raw .eml
     files" (lines 62-75, the UTF-8 regression guard) still passes.

3. **Full legacy suite in shuffled order**
   Check: `TZ=UTC npm run smoke`. The only acceptable failure is
   `legacy/test/rules/assign-round-robin.test.js`, which is listed in `KNOWN_FAILURES.md` as FD-03.

4. **Definition of done**
   Check: `TZ=UTC npm run check`, which runs lint (ESLint on legacy CommonJS), Prettier, typecheck
   (JSDoc types in `parse.js`, so add a `@param {Buffer} raw` / `@returns {string}` comment on the
   new helper) and the unit tests. If the round-robin test fails, report it as known.
   - The orchestrator or user runs `npm run feature:check -- FD-02` (not run during triage).

5. **Manual check (for the user, not the agent).** After `npm run reset`, ticket #36 should read
   "Épreuves des cartes de visite : délai de livraison?". Dropping `poster-reprint-quote` should
   create "Devis pour une réimpression d'affiches" from "Renée Dubé". The `desk-scenario` skill
   covers this.

No changes are needed in `packages/contract`, `apps/api`, `apps/web`, `ops/crontab`,
`legacy/export/nightly-csv.js`, the seed data or the schema. All of them pass these strings through
unchanged.

Change `vendor/mailparse-lite/index.js:52` to

## Failing test proposal

Location: `legacy/test/ingest.test.js`, inside `describe('pollOnce', ...)`, after "ingests raw
.eml files". The file already imports `fs`, `path`, `config`, `all` and `pollOnce`. The second
case also needs `const parseFile = promisify(require('../ingest/parse').parseFile);`.

```js
it('decodes ISO-8859-1 encoded words in the subject and sender name', async () => {
  fs.copyFileSync(
    path.join(config.fixturesDir, 'poster-reprint-quote.eml'),
    path.join(config.inboxDir, 'poster-reprint-quote.eml'),
  );

  await pollOnce();

  const [ticket] = await all('SELECT subject FROM tickets', []);
  expect(ticket.subject).toBe("Devis pour une réimpression d'affiches");
  const [message] = await all('SELECT from_name FROM messages', []);
  expect(message.from_name).toBe('Renée Dubé');
  const [customer] = await all('SELECT name FROM customers', []);
  expect(customer.name).toBe('Renée Dubé');
});

it('decodes ISO-8859-1 B words, lowercase labels, mixed text and folds', async () => {
  const file = path.join(config.inboxDir, 'latin1.eml');
  fs.writeFileSync(
    file,
    [
      'From: =?iso-8859-1?B?UmVu6WUgRHVi6Q==?= <renee@example.com>',
      'Subject: Re: =?iso-8859-1?b?yXByZXV2ZXM=?= et =?ISO-8859-1?q?d=E9lai?=',
      '  ok',
      '',
      'Hi',
    ].join('\r\n'),
  );

  const mail = await parseFile(file);

  expect(mail.subject).toBe('Re: Épreuves et délai ok');
  expect(mail.from.name).toBe('Renée Dubé');
});
```

- `config.fixturesDir` is set from `MAILROOM_FIXTURES` in `legacy/test/setup.js`, and
  `legacy/lib/drop.js` uses it the same way.
- The first case uses the database, so it depends on the `beforeEach` that empties the tables. The
  second calls only the parser and reads nothing from the database.

Expected failure on main, an assertion failure rather than an import error, because the parser
silently produces U+FFFD:

- Case 1: `expected 'Devis pour une r�impression d'affiches' to be 'Devis pour une réimpression d'affiches'`.
- Case 2: `expected 'Re: �preuves et d�lai ok' to be 'Re: Épreuves et délai ok'`.

I confirmed both values by running the parser directly on main. They fail for exactly the reason
the spec gives: Latin-1 accented characters are replaced by replacement characters.

Command: `TZ=UTC npx vitest run --project legacy test/ingest.test.js -t "ISO-8859-1"`. Vitest
project paths are relative to the project root `./legacy`. If the filter doesn't match, use
`legacy/test/ingest.test.js`.

## Risks

- **Body must not be touched.** Rewrite only the header block. A body that quotes a literal
  `=?ISO-8859-1?...?=` would otherwise be changed. Bodies in other charsets are out of scope.
- **Raw 8-bit header bytes** (Latin-1 bytes not wrapped in encoded words) still come out as U+FFFD,
  because `index.js:115` and the helper both decode the buffer as UTF-8. This is out of scope: the
  spec is about encoded words, and the fixtures use encoded words only.
- **Charset aliases.** `latin1`, `ISO8859-1`, `windows-1252` and RFC 2231 language suffixes
  (`ISO-8859-1*fr`) won't match a strict `iso-8859-1` label. The spec limits scope to ISO-8859-1,
  so match exactly, case-insensitively. Node's `latin1` decoder maps 0x80-0x9F to C1 controls, which
  is correct ISO-8859-1 (not cp1252).
- **Existing databases are not healed.** Tickets already ingested keep their garbled subject and
  `messages.from_name`. `customers.name` is first-write-wins (`legacy/models/customer.js:27`): it
  is only filled when it is null, so a customer stored with a garbled name stays garbled even after
  new mail arrives. The spec handles this with `npm run reset` (AC4). No migration is planned (see
  Open questions).
- **Don't break patch 1.** Re-emit Latin-1 words as encoded words rather than decoding them to
  plain text in place. Otherwise the whitespace between a Latin-1 word and an adjacent UTF-8 word
  would no longer be dropped.
- **Traps checked and not touched by this change:**
  - The fix writes no `status`, `created_at` or `closed_at`. The `status`/`state` mirror (issue
    #142) and the `sla:<id>` cache in `legacy/lib/cache.js` are unaffected.
  - The legacy-adapter boundary is unaffected, because nothing in `apps/api` changes.
  - `legacy/config.js` is read once at require time, which matters only for tests. The new tests
    rely on `legacy/test/setup.js` as the existing ones do.
  - `ops/crontab` and `legacy/export/nightly-csv.js:61` export `c.name` and `t.subject` as UTF-8
    text. Those strings were already non-ASCII (U+FFFD), so finance's import sees no new class of
    character.
- **Known failure:** `npm run check` and `npm run smoke` may show
  `legacy/test/rules/assign-round-robin.test.js` (FD-03, `KNOWN_FAILURES.md`). It is not caused by
  this change.
- **JSON inbox mail is unaffected.** The spool pre-processor has already decoded it
  (`parse.js:38-48`).

   `customers.name` won't heal on its own.

   should we keep strictly to the spec's two charsets?
