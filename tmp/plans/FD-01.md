# FD-01: Tag counts in the sidebar (plan)

## Summary

`GET /api/tags` returns only `id`, `name` and `color`, ignores its query string, and the inbox's Tags
sidebar fetches it once with no notion of the status the inbox is showing. FD-01 needs a
`ticketCount` per tag (optionally scoped by `status`, with unknown statuses rejected), the contract
and generated types to describe it, and the sidebar to request counts for the current status and
render them after each tag name. It is a read-only feature: no ticket writes, no mailroom change.

## Kind

missing-feature

## Root cause (what is absent, with evidence)

Contract

- `packages/contract/openapi.yaml:220-231`: `GET /tags` (`listTags`) has no `parameters` and no
  `400` response; its items are `#/components/schemas/Tag`.
- `packages/contract/openapi.yaml:406-416`: `Tag` has `required: [id, name, color]`, no
  `ticketCount`. `Tag` is also embedded in `Ticket.tags` (`openapi.yaml:470-473`) and returned by
  `POST /tags` and `PUT/DELETE /tickets/{id}/tags/{tagId}` (`openapi.yaml:152-183, 246`).
- `packages/contract/src/generated/schema.d.ts:611-617`: `operations.listTags.parameters.query` is
  `never`.
- `packages/contract/src/index.ts:16`: exports `Tag`; `TICKET_STATUSES` at `index.ts:23-27`.
- Generator: `openapi-typescript` `^7.13.0` (`packages/contract/package.json:15`), run with no flags
  (`package.json:11`). The only existing `allOf` (`TicketDetail`, `openapi.yaml:531-540`) gives its
  inline member a `properties` block; that matters for step 1.

API

- `apps/api/src/tags/tags-router.ts:22-24`: `router.get('/tags', (_req, res) => ...)` never reads
  `req.query`, so `?status=bogus` returns 200 today (criterion 5 fails) and no status scoping is
  possible (criterion 4 fails).
- `apps/api/src/tags/tags-repository.ts:16-21`: `listTags` runs
  `SELECT id, name, color FROM tags ORDER BY name`; no count. `toTag` (`:12-14`) drops anything
  else.
- `apps/api/src/tags/tags-schemas.ts:1-11`: only `tagInputSchema`; no query schema. The pattern to
  copy is `apps/api/src/tickets/tickets-schemas.ts:5-11` (`ticketStatusSchema.optional()`) and
  `apps/api/src/tickets/tickets-router.ts:36` (`parse(listTicketsQuerySchema, req.query)`), which
  produces a 400 through `apps/api/src/http.ts:22-35`.
- Express is 5.2.1 with the default `'simple'` query parser
  (`node_modules/express/lib/application.js:97`; nothing in `apps/api/src` overrides it), so a
  repeated `?status=open&status=closed` arrives as an array and `z.enum` rejects it.

Web

- `apps/web/src/tags/tags-api.ts:5-7`: `listTags()` always requests `/tags`.
- `apps/web/src/tags/tag-sidebar.tsx:9`: `useApi<Tag[]>(listTags, 'tags')`, a fixed key, so
  switching Open/Pending/Closed/All never refetches (criterion 2). `tag-sidebar.tsx:26-27` renders
  only the dot and `tag.name` (criterion 1).
- `apps/web/src/tickets/inbox-page.tsx:24` already derives the inbox status (`'open'` by default,
  `undefined` for All or an unknown value) and `inbox-page.tsx:58` renders `<TagSidebar />` without

  gets nothing.
- `apps/web/src/tags/tag-sidebar.tsx:18-23` builds the filter link (criterion 7). It must not
  change.
- `apps/web/src/app.tsx:23-31`: the inbox and the ticket detail page are sibling child routes, so
  leaving the detail page remounts `InboxPage` and its sidebar refetches.

## Implementation plan

1. **Contract** (`packages/contract/openapi.yaml`)
   - Add to `GET /tags`:
     ```yaml
     parameters:
       - name: status
         in: query
         description: Count only tickets in this status. Without it, count every ticket.
         schema:
           $ref: '#/components/schemas/TicketStatus'
     ```
     and a `'400': $ref: '#/components/responses/BadRequest'` response. Change the `200`
     description to `Every tag, with its ticket count.` and point its `items` at
     `#/components/schemas/TagWithCount`.
   - Add an optional property to `Tag` (after `color`; leave `required: [id, name, color]` alone):
     ```yaml
     ticketCount:
       type: integer
       description: Tickets carrying this tag. Present on GET /tags (see TagWithCount).
     ```
   - Add a new schema right after `Tag`. The inline member **must** repeat `ticketCount` under
     `properties`, as `TicketDetail` does (`openapi.yaml:531-540`):
     ```yaml
     TagWithCount:
       allOf:
         - $ref: '#/components/schemas/Tag'
         - type: object
           required: [ticketCount]
           properties:
             ticketCount:
               type: integer
               description: Tickets carrying this tag, scoped by the status query parameter.
     ```
     Do not write the inline member as `{type: object, required: [ticketCount]}` with no
     `properties`: openapi-typescript then emits `components["schemas"]["Tag"] &
Record<string, never>`, which makes `id`, `name` and `color` `never` (observed; see Review log,
     Round 1, Q1). The block above generates
     `TagWithCount: components["schemas"]["Tag"] & { ticketCount: number }`.
   - Export it from `packages/contract/src/index.ts` next to `Tag` (`:16`):
     `export type TagWithCount = Schemas['TagWithCount'];`.
   - Run `npm run generate`, keep `packages/contract/src/generated/schema.d.ts` in the change.
   - Check: `npm run generate && git diff --stat packages/contract`, then read the generated file:
     `operations.listTags.parameters.query` is

     `components["schemas"]["TagWithCount"][]` and

     `TagWithCount` is the intersection above (no `Record<string, never>`). Then
     `npm run typecheck --silent`.

   SELECT g.id, g.name, g.color,
          (SELECT count(*) FROM ticket_tags tt JOIN tickets t ON t.id = tt.ticket_id

     FROM tags g

   Build the `AND t.status = ?` fragment conditionally (driver is `node:sqlite` `DatabaseSync`,

## Failing test proposal

Location: `apps/api/src/tags/tags.test.ts` (new `it` inside the existing `describe('tags')`; the

```ts
it('counts tickets per tag, scoped by status', async () => {
  const tag = await createTag('fd01-count');
  const unused = await createTag('fd01-unused');
  const a = await desk.receive({ from: 'pat@example.com', subject: 'Counted open' });
  const b = await desk.receive({ from: 'quin@example.com', subject: 'Counted closed' });
  await request(desk.app).put(`/api/tickets/${a}/tags/${tag.id}`).expect(200);
  await request(desk.app).put(`/api/tickets/${b}/tags/${tag.id}`).expect(200);
  await request(desk.app).patch(`/api/tickets/${b}/status`).send({ status: 'closed' }).expect(200);

  type Counted = Tag & { ticketCount?: number };
  const count = async (query: string, id: number) => {
    const res = await request(desk.app).get(`/api/tags${query}`).expect(200);
    return (res.body as Counted[]).find((t) => t.id === id)?.ticketCount;
  };

  expect(await count('', tag.id)).toBe(2);
  expect(await count('?status=open', tag.id)).toBe(1);
  expect(await count('?status=closed', tag.id)).toBe(1);
  expect(await count('?status=pending', tag.id)).toBe(0);
  expect(await count('?status=open', unused.id)).toBe(0);

  await request(desk.app).delete(`/api/tickets/${a}/tags/${tag.id}`).expect(200);
  expect(await count('?status=open', tag.id)).toBe(0);

  await request(desk.app).get('/api/tags?status=bogus').expect(400);
  const repeated = await request(desk.app).get('/api/tags?status=open&status=closed').expect(400);
  expect(Array.isArray((repeated.body as { issues?: unknown }).issues)).toBe(true);
});
```

## Risks

- **Contract shape vs held-out typecheck.** `npm run typecheck` also runs
  `tsc -p acceptance/tsconfig.json` (root `package.json:27`). Making `ticketCount` required on
  `Tag` breaks every `Tag`-typed literal without it, including `makeTicket({ tags: [billing] })` in
  web tests (`inbox-page.test.tsx:8,15`), and forces counts into `Ticket.tags`, `POST /tags` and the
  per-ticket tag endpoints. A separate schema with `Tag` unchanged breaks any code that writes
  `ticketCount` in a `Tag`-typed object literal (excess property check) or reads it off a `Tag`.
  The hybrid (optional on `Tag`, required on `TagWithCount`) compiles in both cases, **provided**
  `TagWithCount`'s inline `allOf` member declares `properties.ticketCount` (step 1). Checked in a
  scratch copy: with the step 1 YAML, `{ id, name, color, ticketCount }` is assignable to
  `TagWithCount`, `{ id, name, color }` is rejected for missing `ticketCount`, `{ id, name, color }`
  is still a valid `Tag`, and `TagWithCount['ticketCount']` is `number`.
- **Accessible name and text change.** The sidebar link's name and text become "billing N"; any
  test that finds it with an exact `name: 'billing'` or `getByText('billing')` scoped to the Tags
  nav breaks (`inbox-page.test.tsx:64`). Row-scoped queries such as `inbox-page.test.tsx:39` are
  unaffected. `aria-hidden` on the count is not used.
- **Mock router exact matching** (`apps/web/test/mock-api.ts:35-38`): a missing mock returns 404;
  on first load the sidebar is then empty, and after a status switch `useApi` keeps the previous
  counts (`use-api.ts:36`), so a missing mock shows stale numbers rather than failing loudly.
- **Two `useApi` callers share the `'tags'` key today**; giving the sidebar its own key is fine
  because `useApi` keys are per-component state (`apps/web/src/use-api.ts:22-25`), not a shared
  cache.
- **SQL zero-count trap**: a `LEFT JOIN ... WHERE t.status = ?` drops tags with no matching tickets
  (criterion 3). Use the correlated subquery or put the filter in the `ON` clause.
- **Pre-existing, out of scope**: `setTicketStatus` (`apps/api/src/tickets/tickets-repository.ts:108-116`)
  changes `status`/`closed_at` with plain SQL and does not clear `sla:<id>`, which `CLAUDE.md` says
  it must; `legacy-adapter.ts:29` exposes only `cache.clear()`. FD-01 does not touch it; worth a
  separate item.

## Open questions for the user

1. Contract shape: the plan uses the hybrid (optional `ticketCount` on `Tag`, required on a new
   `TagWithCount` returned by `GET /tags`, with the inline `properties` block from step 1). The
   alternatives are a required `ticketCount` on `Tag` everywhere (counts would then also appear on
   `Ticket.tags` and the per-ticket tag responses) or `TagWithCount` with `Tag` unchanged.
   Assumption: hybrid. The cost is that `Tag`'s type advertises an optional `ticketCount` on
   endpoints that never send it.
2. Should the sidebar counts refresh after "Simulate incoming email" delivers mail (the rules can
   tag it)? The spec only requires the API to be fresh (criterion 4). Assumption: **yes**; step 7
   wires `onDelivered` to bump the sidebar's `refresh` prop, and step 8 tests it. Tagging on the
   detail page needs no wiring, because returning to the inbox remounts it (`app.tsx:23-31`).
3. Should the count ignore the active tag filter? Assumption: **yes**; counts follow status only,
   as criterion 2 says.
4. Should the count be styled apart from the name (muted, right-aligned)? The spec only says
   "after the tag's name (for example, "billing 4")" (`specs/FD-01.md:11`). Assumption: **no**;
   name and count are one plain text run "billing 4", which keeps the link findable by that exact
   text and accessible name. Styling it separately would need a child element and would make
   `getByText('billing 4')` stop matching.

## Review log

### Round 1 (junior-engineer review)

- **Q1 (blocking): `TagWithCount` YAML generates unusable types.** Confirmed. In a scratch copy of
  `openapi.yaml` run through the repo's `openapi-typescript`, the round-0 YAML
  (`allOf: [$ref Tag, {type: object, required: [ticketCount]}]`) produced
  `TagWithCount: components["schemas"]["Tag"] & Record<string, never>`, and
  `tsc --strict` rejected `{ id: 1, name: 'billing', color: '#2b6cb0', ticketCount: 4 }` with
  "Property 'id' is incompatible with index signature". Two shapes work: an inline member with
  `properties.ticketCount` (generates `Tag & { ticketCount: number }`) and an outer
  `required: [ticketCount]` beside `allOf` (generates `WithRequired<Tag, "ticketCount">`). Step 1
  now gives the exact YAML for the first, because it matches the existing `TicketDetail` pattern
  (`openapi.yaml:531-540`) and does not depend on `Tag` declaring the property. The hybrid stays
  the choice: with the fixed YAML it typechecks for the `TagWithCount` literal, the `Tag` literal
  without a count, the rejected `TagWithCount` without a count, and `listTags` query and response
  types. Risks and Open question 1 updated. The DoD checks for no `Record<string, never>`.
- **Q2: count markup vs a plain text query.** Resolved from the spec's example
  (`specs/FD-01.md:11`): render ``{`${tag.name} ${tag.ticketCount}`}`` as one text node, so
