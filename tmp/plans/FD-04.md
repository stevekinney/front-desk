# FD-04: Pending-customer pauses the SLA clock (triage plan)

## Summary

Nothing in the system knows that a `pending` ticket should stop the SLA clock. The SLA is computed only from `created_at`, `status` and `closed_at`, and nothing records when a ticket went pending or for how long. So a pending ticket counts down like an open one and goes `breached`. Separately, the API changes status with raw SQL on its own connection, which skips `Ticket.afterSave`. That hook is the only thing that clears the mailroom's per-ticket SLA cache, so after any read the next status change is invisible to the SLA. This is the "badge is sometimes just wrong after a ticket is paused or closed" report. Both mechanisms were reproduced on `main`.

A third, pre-existing defect sits under criterion 3: `isBusinessHour` counts 17:00-17:59 New York as business time, so a pause that spans an evening banks 60 minutes too many per evening. The plan fixes it here (see C and step 3a); that is the default answer to open question 2.

## Kind

Missing feature (criteria 1-4, 6, 7), plus one real bug (stale SLA cache) behind criterion 5, plus a one-character business-hours fix that criterion 3 depends on.

## Root cause (with path:line evidence)

### A. No pause concept anywhere (criteria 1-4, 7)

- `legacy/lib/sla.js:135-143`: `snapshot()` computes the due time as `addBusinessMinutes(created_at, 8h)` and nothing else. It carries only `status`, `dueAt` and `closedAt`.
- `legacy/lib/sla.js:150-174`: `summarize()` has two branches: `closed` gives `met`/`missed`, and everything else, `pending` included, counts down and turns `breached` at `sla.js:166`. There is no `paused` branch.
- `legacy/lib/sla.js:127`: the JSDoc state union is `'on-track' | 'at-risk' | 'breached' | 'met' | 'missed'`, with no `paused`.
- `legacy/db/schema.sql:18-28`: `tickets` has no column for when a pause started or how much paused time has built up. No other table records it either.
- `legacy/models/ticket.js:61-76`: `Ticket.updateStatus` only sets `status` and `closed_at`, so it starts no pause and banks none.
- `packages/contract/openapi.yaml:434-440`: the `Sla.state` enum lacks `paused`, and the `remainingMinutes` description ("Null when closed") needs to cover paused tickets. Generated copy: `packages/contract/src/generated/schema.d.ts:270`. Duplicated union: `apps/api/src/legacy-adapter.ts:16`.
- Repro (scratch script, throwaway DB): created Monday 09:00 NY and moved to `pending`. A day later `forTicket` returns `{ state: 'breached', remainingMinutes: -480 }`.

### B. API status writes don't invalidate the SLA cache (criterion 5)

- `apps/api/src/tickets/tickets-repository.ts:108-116`: `setTicketStatus` runs `UPDATE tickets SET status, state, updated_at, closed_at` on the API's own `DatabaseSync` connection. The state mirror is correct. It does not go through the `Ticket` model, so `Ticket.afterSave` (`legacy/models/ticket.js:44-49`, the only `cache.del('sla:'+id)`) never runs.
- `legacy/lib/sla.js:182-194`: `forTicket` returns the cached snapshot when one exists. The snapshot holds `status` and `closedAt` (`sla.js:138-141`), so a stale snapshot gives the old state. `legacy/lib/cache.js:5-8`: entries never expire.
- `apps/api/src/tickets/tickets-router.ts:48-54`: PATCH calls `setTicketStatus` and then `loadTicket` → `withSla` → `getSla` (`with-sla.ts:8`). After any earlier GET of that ticket, the PATCH response and every later read return the pre-change SLA.
- It "fixes itself later" because something else eventually re-saves that ticket through the model, for example new mail being threaded on or a rule assigning it, and that clears the entry. A restart does the same.
- Why the existing test passes: `apps/api/src/tickets/tickets.test.ts:79-92` closes a ticket that has never been read, so nothing was cached.
- Repro, run as a scratch Vitest file against the real `createTestDesk()`: GET `/api/tickets/:id`, then PATCH `closed`. The response has `sla.state === 'on-track'` and a numeric `remainingMinutes`, where `met`/`null` was expected. The same happens with `pending`.
- Other raw-SQL status writer: `apps/api/src/seed/seed.ts:63-74`. It runs at seed time, before any SLA read (`apps/api/src/server.ts:14` seeds, `:20` starts the poller; the API is the only caller of `forTicket`, via `with-sla.ts:8`), so the cache is harmless there, but it never sets pause data (see step 6).
- Cross-process variant, not fixed here (open question 4): `legacy/bin/sweep-rules.js` runs hourly in its own process (`ops/crontab:15`), and `auto-close-stale` closes only `pending` tickets (`legacy/rules/auto-close-stale.js:19,32`). Its `afterSave` clears the sweep process's cache, not the API's.

### C. The 17:00 hour counts as business time (criterion 3; also FD-07 criterion 4)

- `legacy/lib/sla.js:54-56`: `isBusinessHour` is `hour >= config.sla.openHour && hour <= config.sla.closeHour`, with `closeHour: 17` (`legacy/config.js:55`). The comment at `sla.js:50` says "9 to 5, inclusive", so a desk day is 9 hours.
- `docs/architecture.md:72-74` defines business hours as 09:00 to 17:00 and the SLA as 8 business hours. The FD-04 spec points there ("The SLA is measured in business time. See `docs/architecture.md`"). `specs/FD-07.md` criteria 1 and 4 say the same: a day runs from `openHour` up to, but not including, `closeHour`.
- Measured with a scratch script against `main` (TZ=UTC, throwaway env): `businessMinutesBetween(Mon 17:00 NY, Mon 18:00 NY) = 60`; Fri 16:00 → Mon 10:00 NY = 180; Mon 11:00 → Tue 11:00 NY = 540; `addBusinessMinutes(Mon 10:00 NY, 480)` = Mon 18:00 NY. With `<` the same calls give 0, 120, 480 and Tue 10:00 NY.
- So on `main`, a pause that spans an evening banks 60 extra minutes per evening, against criterion 3 ("time spent pending outside business hours adds nothing").
- Blast radius, measured: in a scratch copy of the repo with only `<=` changed to `<`, `TZ=UTC npx vitest run` passes 17 files / 107 tests, the same as unchanged. Existing tests never cross a 17:00 hour (`legacy/test/sla.test.js` arrives at 09:00 or in the evening). Real due times do change: any ticket whose created→due window crosses a 17:00 hour (any weekday arrival after 09:00) becomes due up to an hour later per crossed evening, so live and demo badges move.

## Implementation plan

The design choice is **one writer for status**. Business-minute math lives only in `legacy/lib/sla.js`, and only `apps/api/src/legacy-adapter.ts` may import legacy. So starting a pause on `→ pending` and banking business minutes on `pending → open|closed` belongs in `Ticket.updateStatus`. The API calls that through a new adapter wrapper instead of its own SQL. Three things follow from this:

- `afterSave` clears the cache, which fixes B for every API-originated change.
- `beforeSave` keeps the `status`/`state` mirror (issue #142).
- The rules (`legacy/rules/context.js:90-97`), including `auto-close-stale` from the hourly cron sweep (`ops/crontab:15`, `legacy/bin/sweep-rules.js`), already call `Ticket.updateStatus`, so they finish pauses correctly with no change to `legacy/rules/`.

CLAUDE.md's narrower suggestion, an adapter `clearSlaCache(id)` that calls `cache.del`, would fix B alone. It would leave two writers that both have to do the pause bookkeeping, and the API's writer can't reach the business-minute math. If the API keeps raw SQL for some reason, it must also call a new adapter `clearSlaCache(id)` wrapping `cache.del('sla:' + id)`, not `closeLegacy()`.

Time units: paused time is banked in **whole business minutes** (`paused_minutes INTEGER`), floored per pause exactly as `businessMinutesBetween` already floors (`sla.js:90`). `addBusinessMinutes` takes minutes and the contract's `remainingMinutes` is an integer, so milliseconds would buy nothing visible. A pause that starts or ends off a minute boundary can make `remainingMinutes` after a resume one less than the frozen value; no criterion pins that, and all tests use whole-minute instants.

1. **Schema: pause columns with an idempotent migration.**
   - Add `paused_at TEXT` and `paused_minutes INTEGER NOT NULL DEFAULT 0` to `CREATE TABLE IF NOT EXISTS tickets` in `legacy/db/schema.sql`, for new databases.
   - Existing databases: SQLite has no `ADD COLUMN IF NOT EXISTS`, and `migrate()` (`legacy/db/connection.js:114-121`) just `exec`s the file, so a bare `ALTER TABLE` in `schema.sql` would fail on the second start. In `migrate()`'s deferred work, after `exec(schema)`, read `PRAGMA table_info(tickets)` and, for each missing column, `ALTER TABLE tickets ADD COLUMN ...`.
   - Backfill only inside that "column was just added" branch: `UPDATE tickets SET paused_at = updated_at WHERE status = 'pending' AND paused_at IS NULL`. `updated_at` is the best available guess for when a teammate set the ticket pending. It does not run on later starts; NULL is safe afterwards because of the null rule in step 2.
   - This is raw SQL inside `legacy/`. CLAUDE.md's "write through the models" rule can't apply here: `connection.js` is below the models (they require it), the schema exists only after this runs, and going through `Ticket.save` would bump `updated_at` (`legacy/models/ticket.js:42`), which resets `auto-close-stale`'s idle clock (`legacy/rules/auto-close-stale.js:29`). No SLA has been cached at migrate time in any process (the API migrates at startup, `apps/api/src/server.ts:14-17`).
   - Keep the callback style, with no promises (CLAUDE.md).
   - Alternative: a `ticket_pauses(ticket_id, started_at, ended_at)` table. It is idempotent through `CREATE TABLE IF NOT EXISTS` and keeps each interval. But `snapshot()` would need a second async query, and every writer would need a new model. Columns keep the SLA a one-row read.
   - Add both columns to the `Ticket` model's `columns` list (`legacy/models/ticket.js:27-36`). Otherwise `hydrate` (`legacy/lib/model.js:36-43`) drops them and `save()` overwrites nothing.
   - In `beforeSave` (`legacy/models/ticket.js:37-43`):
     - Default `paused_minutes`, the same way `status` is defaulted at `:39`: `if (ticket.paused_minutes == null) ticket.paused_minutes = 0;`. `save()` inserts every listed column explicitly (`legacy/lib/model.js:149-151, 159-177`), and the constructor sets missing ones to `null` (`model.js:40-42`). Without the default, SQLite's `DEFAULT 0` never applies and every `Ticket.create` fails with `NOT NULL constraint failed: tickets.paused_minutes`, which breaks ingest, seed and every test's `receive()`.
     - Stamp a pause that has no start: `if (ticket.status === 'pending' && !ticket.paused_at) ticket.paused_at = now;`. This makes `Ticket.create({ status: 'pending' })` (as in `legacy/test/rules/apply-to.test.js:38-42`) start its pause at creation.
   - Do not touch the `state` column, the `sla_report` view (`legacy/db/schema.sql:60-69`) or `legacy/export/nightly-csv.js`.
   - New test file `legacy/test/migrate.test.js` (picked up by `vitest.config.ts:30`, `include: ['test/**/*.test.js']`). The project setup (`legacy/test/setup.js:8-12`) gives the file its own empty database, and `connection.js:19-33` opens it lazily, so:
     - Before the file's first `migrate()`, create `customers` and the **old** `tickets` table with `run()` from `legacy/test/helpers.js`, using an inline copy of `legacy/db/schema.sql:10-28` as it is on `main` (comment it as a snapshot of the pre-FD-04 DDL).
     - Insert one `pending` row (with `updated_at` set) and one `open` row with raw SQL.
     - `await migrate(); await migrate();` resolves with no error.
     - `PRAGMA table_info(tickets)` lists `paused_at` and `paused_minutes`.
     - The pending row has `paused_at` equal to its `updated_at` and `paused_minutes` 0; the open row has `paused_at` NULL.
   - Check: `TZ=UTC npx vitest run --project legacy test/migrate.test.js test/model.test.js`.

2. **Mailroom: pause bookkeeping in `Ticket.updateStatus`** (`legacy/models/ticket.js:61-76`).
   - When the new status is `pending`, set `paused_at = clock.isoNow()`.
   - When the old status was `pending` and the new one isn't: if `paused_at` is set, add `businessMinutesBetween(new Date(paused_at), clock.now())` to `paused_minutes`; in every case set `paused_at = null`.
   - Null rule: `paused_at == null` while leaving `pending` means nothing to bank. Never call `new Date(null)`: that is the 1970 epoch, and `businessMinutesBetween` would walk about 500,000 hours of `formatToParts` before returning roughly 56 years of minutes. After step 1's `beforeSave` stamp and backfill, NULL can only come from a raw-SQL writer.
   - `sla.js` requires `models/ticket` at the top (`sla.js:14`), so require `../lib/sla` lazily inside the function. `legacy/db/connection.js:45-46` does the same.
   - The existing early return when the status is unchanged (`ticket.js:68`) already stops pending→pending from resetting the pause.
   - Extend `legacy/test/rules/apply-to.test.js:72-84` ("reopens a ticket when the customer writes back"), which already goes pending → open through `reopen-on-reply` and `context.js:91` → `Ticket.updateStatus`: select `status, state, paused_at, paused_minutes` and expect `{ status: 'open', state: 'active', paused_at: null, paused_minutes: 0 }`. The clock isn't frozen there, but creation and reopen are milliseconds apart, so the banked value floors to 0 at any time of day.
   - Add to `legacy/test/model.test.js`: `Ticket.create({ ..., status: 'pending' })` with a frozen clock stores `paused_at` equal to that instant and `paused_minutes` 0; `Ticket.create` with no status stores `paused_at` NULL and `paused_minutes` 0.
   - Check: `TZ=UTC npx vitest run --project legacy test/model.test.js test/rules/apply-to.test.js`.

3. **Mailroom: business hours and `paused` in the SLA math** (`legacy/lib/sla.js`).

   3a. Fix the closing hour: `sla.js:55` becomes `hour < config.sla.closeHour`, and the comment at `:50` becomes "09:00 up to, not including, 17:00" (it would otherwise lie). This is the default answer to open question 2. It also satisfies FD-07 criterion 4 ahead of FD-07; FD-07 still has to make the hours configurable, and nothing here conflicts with that.

   3b. Pause math:
   - `snapshot()` adds `pausedAt` (`paused_at || null`) and `pausedMinutes` (`paused_minutes || 0`), and computes the banked due time `dueAt = addBusinessMinutes(created_at, config.sla.hours * 60 + pausedMinutes)`. That moves the due time later by the banked business minutes (criteria 3 and 4). This is what gets cached.
   - `summarize()` checks `status === 'pending'` after the `closed` branch and before the countdown. Two different due times are involved; keep them apart:
     - `dueBanked = new Date(snap.dueAt)` (completed pauses only) drives `remainingMinutes`. With `pausedAt = snap.pausedAt ? new Date(snap.pausedAt) : now` (null rule), `remainingMinutes = pausedAt < dueBanked ? businessMinutesBetween(pausedAt, dueBanked) : -businessMinutesBetween(dueBanked, pausedAt)`. It does not depend on `now`, so it is frozen (criterion 2).
     - `dueProjected = addBusinessMinutes(dueBanked, businessMinutesBetween(pausedAt, now))` is the reported `dueAt`: the due time if the ticket resumed now (open question 1). Verified equal to `addBusinessMinutes(created_at, 480 + pausedMinutes + bm(pausedAt, now))` for the step-3 cases.
     - `state: 'paused'`. A paused ticket is never `breached`, `at-risk` or `on-track` (criterion 2), including one that was already overdue when it paused (it keeps its negative `remainingMinutes`; open question 5).
   - Closed tickets are judged against the banked `dueAt`, which already includes the pause that the close just banked (step 2).
   - Update the JSDoc typedefs (`sla.js:115-129`): `SlaSnapshot` gains `pausedAt: string | null` and `pausedMinutes: number`; `SlaSummary.state` gains `'paused'`; the `remainingMinutes` note says "frozen while paused".

   3c. Tests in `legacy/test/sla.test.js`, all with `clock.freeze` and whole-minute instants. Dates are October 2026, New York on EDT (UTC-4), as the file's header comment at `:15` says.    - Frozen while paused: created Mon 09:00 NY (`2026-10-05T13:00Z`), `updateStatus(pending)` at Mon 11:00 NY (`15:00Z`). At Tue 15:00 NY (`2026-10-06T19:00Z`) `forTicket` gives `state: 'paused'`, `remainingMinutes: 360`, `dueAt: '2026-10-07T17:00:00.000Z'` (Wed 13:00 NY; `main` would give Wed 12:00 NY).
   - Resume: same ticket, `updateStatus(open)` at Tue 11:00 NY (`2026-10-06T15:00Z`). `paused_minutes` is 480 (540); `forTicket` gives `dueAt: '2026-10-06T21:00:00.000Z'` (Tue 17:00 NY) and `remainingMinutes: 360`.
   - Evenings and weekends add nothing: created Fri 09:00 NY (`2026-10-09T13:00Z`), pending at Fri 16:00 NY (`20:00Z`), open at Mon 10:00 NY (`2026-10-12T14:00Z`). `paused_minutes` is 120 (180); `dueAt` is `2026-10-12T15:00:00.000Z` (Mon 11:00 NY).

   - Closed straight from pending: created Mon 09:00 NY, pending Mon 16:00 NY, `updateStatus(closed)` at Tue 10:00 NY (`2026-10-06T14:00Z`). `paused_minutes` is 120 (180), `dueAt` is `2026-10-06T15:00:00.000Z` (Tue 11:00 NY), state `met`. Without the pause it would be `missed` (due Mon 17:00 NY).
   - Overdue when paused: created Mon 09:00 NY, pending at Tue 10:00 NY. At Wed 15:00 NY `forTicket` gives `state: 'paused'`, `remainingMinutes: -60` (-120).
   - Cached read then change: `forTicket`, then `updateStatus(pending)`, then `forTicket` gives `paused` (regression guard for `afterSave`; passes on `main` for `closed` already, `sla.test.js:133-142`).

## Failing test proposal

Primary, in `apps/api/src/tickets/tickets.test.ts`, inside `describe('PATCH /api/tickets/:id/status')`:

```ts
it('pauses the SLA while the ticket is pending', async () => {
  const id = await desk.receive({ from: 'pat@example.com', subject: 'Waiting on you' });
  await request(desk.app).get(`/api/tickets/${id}`).expect(200);

  const res = await request(desk.app)
    .patch(`/api/tickets/${id}/status`)
    .send({ status: 'pending' })
    .expect(200);

});
```

- On `main` it fails with `AssertionError: expected 'on-track' to be 'paused'`. A scratch copy run against the real `createTestDesk()` showed exactly this.

- This is the right failure, because the SLA has no paused state and pending keeps counting down. It also fails for the cache reason, because the GET warms the cache, so the fix has to handle both.
- Command: `TZ=UTC npx vitest run --project api src/tickets/tickets.test.ts -t "pauses the SLA"`

## Risks

- **Issue #142, the `state` mirror.** Moving the API's status writes onto `Ticket.updateStatus` keeps `state` correct through `beforeSave` (`legacy/models/ticket.js:40`). Any new raw-SQL path must still write `state`. Do not touch `nightly-csv.js` columns or the `state = 'resolved'` filter (`legacy/export/nightly-csv.js:61-67`). It runs from cron (`ops/crontab:18`), outside the test suite.
- **Migration idempotency.** A plain `ALTER TABLE ... ADD COLUMN` in `schema.sql` breaks the second start. Guard it in `migrate()` with `PRAGMA table_info`. Test databases are always fresh, so only `migrate.test.js` catches this.
- **`NOT NULL DEFAULT 0` with this model layer.** `save()` writes explicit `NULL`s for unset columns, so `paused_minutes` needs a `beforeSave` default, or every ticket insert fails (step 1).
- **NULL `paused_at` while pending.** Any path that calls `new Date(paused_at)` without the null rule turns NULL into 1970 and hangs for seconds in `businessMinutesBetween`. Steps 2 and 3b both guard it; step 3c tests it.
- **Circular require.** `sla.js` → `models/ticket.js` already exists, so `ticket.js` must require `sla` lazily, or a module-load cycle returns `{}`.
- **Deploy ordering.** `legacy/bin/sweep-rules.js` never calls `migrate()`, and it runs at :05 every hour from the same checkout (`ops/crontab:15`). If the checkout is updated before the API restarts and migrates, the sweep's `Ticket.save` writes `paused_at`/`paused_minutes` to columns that don't exist yet and `auto-close-stale` fails for that run. Rollout assumption: restart the API (which migrates, `server.ts:14-17`) before the next :05. Optional hardening, not required: call `db.migrate` at the top of `sweep-rules.js`.
- **Cross-process cache staleness (open question 4).** `legacy/lib/cache.js` is per process and never expires. When the hourly sweep's `auto-close-stale` closes a pending ticket (`auto-close-stale.js:19,32`), the API server's cached snapshot still says `pending`. After FD-04 that ticket shows up under `?status=closed` (the list filters in SQL, `tickets-repository.ts:64`) wearing a "Paused, overdue …" badge until it is re-saved in the API process or the API restarts. On `main` the same ticket shows "Overdue …" instead of "SLA missed": same bug, different label. Not fixed here by default.
- **The 17:00 fix moves due times.** With step 3a, every ticket whose created→due window crosses a weekday 17:00 NY becomes due up to an hour later per crossed evening, so live badges shift once on deploy, and seed ages (`seed.ts:56`, relative to now) make demo badges move too. The unit suite was measured unaffected (107/107 in a scratch copy). The `sla_report` view's `business_minutes()` (`connection.js:43-48`) uses the same function, so the finance-side business-minute numbers shrink by up to 60 per evening; the export's columns and `state` filter are unchanged.
- **Rounding drift.** Banking floors to whole minutes per pause (`sla.js:90`); see "Time units" above.
- **Time source.** `apps/api/src/database.ts:21-23` `now()` uses the real `Date`, while the SLA uses `legacy/lib/clock.js`. Routing status changes through the mailroom makes `updated_at`, `closed_at` and `paused_at` use the legacy clock, which keeps them consistent with SLA math and freezable in tests.
- **`auto-close-stale` idle time** uses `updated_at` (`legacy/rules/auto-close-stale.js:29`). Pause bookkeeping writes in the same save, so it doesn't change idle behaviour; the migration backfill deliberately doesn't bump `updated_at`. Don't add extra saves that bump `updated_at` on reads.
- **Interplay with other backlog items.** FD-10 rebuilds `tickets` to drop `state` and must carry `paused_at`/`paused_minutes` across. FD-08 ports the rules to TypeScript; its `setStatus` must also go through the same single writer. FD-07 makes hours configurable: banked `paused_minutes` stays correct as long as it's banked when the pause ends, and step 3a already gives FD-07 criterion 4's semantics.
- **The web inbox defaults to `?status=open`** (`apps/web/src/tickets/inbox-page.tsx:24`), so paused tickets show only under the pending filter. Criterion 6's inbox check needs the pending list.

## Open questions for the user

None of these block implementation; each has the assumption the plan now uses.

1. While a ticket is paused, what should `dueAt` show? **Assumption:** the projected due time if it resumed now (`dueProjected` in step 3b), which moves forward continuously. Alternative: the due time from completed pauses only, which may already be in the past.
2. Should FD-04 fix the 17:00-hour bug (`legacy/lib/sla.js:55`, `<=` to `<`) or leave it to FD-07? **Assumption:** fix it in FD-04 (step 3a). `docs/architecture.md:72-74`, the FD-04 spec's pointer to it, and `specs/FD-07.md` criterion 4 all define the day as 09:00 up to 17:00, and criterion 3 is only true under that definition. Cost: due times shift for tickets that arrive after 09:00 (Risks). If you'd rather leave it to FD-07, step 3c says how the tests change.
3. Should the finance export's `business_minutes` (the `sla_report` view) subtract paused time? **Assumption:** no; it is left unchanged because of issue #142, and finance keys on the file's format.
4. Is the cross-process gap in scope: a ticket auto-closed by the hourly cron sweep keeps showing "Paused, overdue …" in the API until the API restarts (Risks)? **Assumption:** follow-up, not FD-04. Criterion 5's "in the response to the status change itself" points at API-originated changes, and the bug exists on `main` with a different label. Cheap fix if you want it now: `forTicket` always reads the row (a primary-key lookup) and caches only the `addBusinessMinutes` result keyed by `created_at` and `paused_minutes`; that makes `afterSave`'s `cache.del` vestigial. Its test would be a raw `run('UPDATE tickets SET status = ...')` after a cached `forTicket`, then `forTicket` again.
5. When a ticket that is already past due goes pending, should the badge say "Paused" with the overdue amount? **Assumption:** yes: state `paused`, negative `remainingMinutes` kept, label "Paused, overdue …".
6. The demo seed's pending tickets pause 24 wall hours after arrival, so they mostly show "Paused, overdue …". **Assumption:** that's fine (it is what such a ticket would really show). Alternative: `paused_at = createdAt + 1h`, so the demo shows "Paused, Nh left".
