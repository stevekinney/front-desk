# FD-07: Business-hours settings drive the SLA

**Size:** M

## Background

The support desk's hours, time zone and SLA length are fixed in code. The desk is about to add an early shift, and the London office wants to run its own desk. These need to be settings that teammates can change, and the SLA badges and the SLA report need to follow them without a restart.

`docs/architecture.md` describes how the SLA is measured.

## Acceptance criteria

1. `GET /api/settings/business-hours` returns `{ "openHour", "closeHour", "timeZone", "slaHours" }`. The defaults are `9`, `17`, `"America/New_York"` and `8`, the values the desk uses today.
2. `PUT /api/settings/business-hours` with all four fields saves them and responds with the saved settings. It responds with `400` and changes nothing if any of these is true:
   - a field is missing;
   - an hour is not a whole number from 0 to 24;
   - `openHour` is not before `closeHour`;
   - the time zone is not a valid IANA zone;
   - `slaHours` is not a whole number of at least 1.

   Saved settings survive a restart.

3. A ticket's SLA (its due time, state and remaining minutes) uses the current settings from the next read on, including for tickets that have already been read.
4. A business day runs from `openHour` up to, but not including, `closeHour`. With the defaults, that is eight business hours from 09:00 to 17:00, Monday to Friday, in the configured time zone.
5. `GET /api/reports/sla` lists every ticket as `{ "ticketId", "status", "businessMinutes" }`. `businessMinutes` counts the business minutes from when the ticket arrived until it was closed, or until now if it is still open, using the current settings.
6. The web app has a "Settings" link in the header. It opens a page with fields labeled "Opens at", "Closes at", "Time zone" and "SLA hours", filled in with the current settings, and a "Save" button.
7. The OpenAPI contract describes the new operations, and the generated types match it.
